# 《游牧工坊》世界物品放置与蓝图施工设计

2026-09-06 扩展方向：小块甲板、墙/门窗/顶棚、支撑关系与局部多层施工按[可扩建甲板方案](nomad-workshop-expandable-decks-design.md)逐步落地。本文已实现的物品区域/租约继续复用；结构施工需要补可达施工位与材料事务，不能把下文计划中的蓝图阶段误认为当前已交付。

## 0. 当前实施进度

Phase A 已完成第一轮闭环：无 Unity 依赖的 `PlacementRegionLedger` 负责有向矩形包含、跨区域重叠、稳定选位以及预留/提交/取消；设施定义可声明局部放置区域，并把水罐停放区作为建造功能净空参与预演。唯一水罐在车辆水箱、居民携带和饮水站之间转移时，会保存稳定区域 id、精确局部姿态和派生世界姿态；检查点按同一真值恢复，View 不再根据设施尺寸猜测偏移。

Phase B 已完成第一条空间与行动闭环：`NomadWorldItemDefinition` 用 ScriptableObject 声明稳定定义 id、类别、毫米占地、安全边距、任意/离散朝向与可替换灰盒样式；野战厨房声明 `countertop-center` 台面区域，第一座厨房只生成一只 `cup-01`，不会让每座厨房凭空复制杯子。杯子与水罐共用同一账本和 Model 修订投影，开发面板可观察 owner/region/local pose；版本 4 检查点用可选 `WorldItems` 集合保存普通落位物品，旧 v4 存档可从第一座稳定台面补出这个开发期初始样本。

N2-A 已完成第一条统一建造纯规则闭环：`NomadConstructionBlueprintLedger` 复用连续占地账本立即占用最终建筑占地；材料只能经 `ResourceFlowLedger` 搬入蓝图的 `ConstructionStaging` 库存，齐料后才能进入施工，工作量完成后还要经过独立 Commissioning 才成为 Complete。取消或成品拆除会从暂存库存取出真实材料批次形成 `NomadConstructionRecovery`，不会传送回来源库存；永久节点、车载设施和途中临时地点的保留判定也以纯路线进度规则锁定。它目前不接正式 Foundation System、场景资产或居民施工动画，下一步是 N2-B 的读模型与可重建场景接线。

`PlacementRegionLedger` 的移动租约会在行动开始时同时锁住精确来源恢复位和目标姿态：拿起后来源不再生成世界物品投影，但仍不可被抢占；成功放下才原子提交目标，取消、死亡、施工改道或半途检查点则精确恢复来源。居民 Harness 已真实执行“走近来源 → 拿起 → 手持移动 → 放到目标”，View 只消费一个稳定的右手携带锚点。它验证了事务和表现接缝，不代表居民已经产生正式喝水/整理动机，也不代表手部 IK 已经交付。

建造模式会同时显示设施交互位与放置区域，离开建造面板则统一执行完整退出命令，清理幽灵、网格和世界诊断。2026-09-05 重审后优先推进完整旅程：本专题的下一份实际消费者应来自必要补给、清运或部署；更多餐具、IK 和完整蓝图暂不阻塞旅途。统一顺序见 Foundation §9。

## 1. Phase A 原本要修正的真实缺口

在 Phase A 之前，Foundation 的水罐虽有稳定实例、容量、预留和“属于哪座设施”的逻辑锚点，但 3D 位置仍由 `NomadFoundationWorldView` 根据设施尺寸加一个侧向偏移得到。那个位置：

- 没有进入连续占地账本，可与新设施、其他物品或居民路线重叠；
- 没有自己的局部姿态存档，读档只能再算同一个偏移；
- 不知道精细模型替换后哪片表面仍可以放物；
- 不能与未来的杯子、盘子、工具、建材堆共用规则。

因此实现选择了可复用的空间语义，而不是继续为水罐增加特例偏移；Phase B 的杯具已经证明这条边界可被第二种物品消费。

## 2. 核心决策：放置区域与交互位分工

一个单独的“空位点”不能同时回答物品能否放下、居民站在哪里、手如何触达三个问题。第一版采用三个小而独立的概念：

| 概念 | 回答的问题 | 典型例子 |
|---|---|---|
| `PlacementRegion` | 这片平面还能在哪里放下什么 | 桌面、柜台、地面堆料区、水箱旁的水罐停放区 |
| `PlacementFootprint` | 物品实际占用多大面积和高度 | 杯子底圆、水罐有向矩形、一捆钢管 |
| `InteractionSlot` | 居民为了拿放/使用应在哪里、朝哪里站 | 柜门前、灶台前、洗手池前 |

`PlacementRegion` 不代替已经成立的设施 `InteractionGroup / Slot`。前者属于物品空间与所有权真值，后者属于居民导航和设施容量真值。一张桌面可有一个大放置区域，但仍只有两个座位交互组。

### 2.1 何时仍使用精确插槽

插头、武器挂架、杯架、机器内部料仓、必须对准枪口或管口的部件，仍可定义为容量一的精确 `PlacementSlot`。它是 `PlacementRegion` 的特化而不是第二套物品系统：同样保存 region/slot id、物品 id、局部姿态和预留。

## 3. `PlacementRegion` 的第一版数据

每个区域是某个支撑对象局部空间中的二维平面。首版只需要有向矩形；只有真实模型需要 L 形或孔洞时，再扩展为多边形或多子区域。

区域定义至少包含：

- 稳定 `regionId`、所属设施/甲板/地形的稳定 id；
- 局部中心、方向、宽深和支撑高度；
- 用途标签，例如 `FoodSafe`、`TemporaryDrop`、`ToolStorage`、`ConstructionStaging`、`GroundStockpile`；
- 可接受物品类别、单件/总质量、高度、堖叠和姿态约束；
- 内缩安全边距，避免物品紧贴台面边缘或穿过挡板；
- 当前放置记录和已预留候选姿态。

物品的 `PlacementFootprint` 至少包含：

- 二维占地形状、安全边距、高度和质量；
- 允许的放置方向，例如杯子可任意旋转，水罐只取 0/90 度；
- 是否必须竖直、是否可堆叠、可以承载什么；
- 精确拿取/放下的视觉锚点，它不参与几何容量计算。

定义属于设施数据或 Prefab 的可视化 Authoring 组件，不在饮水、进食或建造 System 里硬编坐标。精细模型替换时可以修改区域数量和尺寸，但已发布存档所用的 `regionId` 需要保留或提供迁移。

## 4. 如何判断“还能放下”

第一版使用确定性二维几何，不依赖刚体自由落体：

1. 根据物品允许的方向，从区域角、边界和已有物品边缘生成有限候选位；
2. 用有向矩形（圆形物可用内切/外包圆）检查是否完全位于区域内、是否越过安全边距、是否与已有/预留物品相交；
3. 通过用途、质量、高度、污染和堆叠规则后，按稳定排序选出一个姿态；
4. 任务先原子预留“物品 + 来源 + 目标姿态”，居民到位后才在动作提交点转移所有权。

算法不需要为桌面生成可见网格，也不必对每帧每个区域穷举。只有候选搬运/放置任务询问容量时计算，结果可按区域修订号缓存。

### 4.1 不默认“把旧物品自动挤一挤”

在无动画、无居民动作的情况下自动重排现有物品，会造成物体瞬移、打破任务预留和玩家记忆，还会让存档的确定性变差。因此默认为：

- 已放下的物品保持实际姿态；
- 放不下就选其他区域、继续携带或生成可解释的阻塞；
- 如果试玩证明“整理桌面/仓库”有价值，它应是真实搬动任务，或是一个明确的玩家重排交易，不是放置账本的隐式副作用。

将来可以在同一区域内对“未预留、无内容溢出风险”的小物件进行少量重排，但必须作为可观察事务实现，并经真实玩法证明值得这份复杂度。

## 5. 地面不是无限多个隐形建筑

甲板、停靠点地面和室内地板本身是 `SupportSurface`，它提供高度、边界、坡度、承载和可建造标签。普通运输任务不应在整片地面随机扔物，而是优先使用：

1. 设施自带的小型停放区，例如车辆水箱的水罐停放区；
2. 玩家在支撑面上画出的“临时放置区 / 堆料区”；它是轻量 Zone，可以没有实体模型；
3. 意外中断时的紧急落地点，它使用就近确定性搜索，落地后成为真实松散物品和导航软障碍/凌乱来源。

玩家无需逐个指定每只水罐的点坐标；他指定“哪片地可以堆什么”，系统在区域中选确定姿态。如果地上松散物导致通道狭窄，它是可见的管理后果，不应被导航层忽略。

## 5.1 车内外统一建造与地点生命周期

车内甲板和车外地面共用同一套蓝图 / 材料 / 工作量事务。玩家先在可达且满足承载条件的空位规划设施占地，蓝图立即占用最终空间；居民把真实材料运到蓝图的 `ConstructionStaging` 区域，材料堆在视觉上占用这片区域，之后居民在可达工作姿态上原地累计工作量，完成后才原子启用设施。车内外的差别只来自 `SupportSurface` 能力、天气暴露、承载和是否随车辆移动。开局只预先提供一张“修复当前车辆最低行驶能力”的蓝图，作为求生教程的一部分；普通设施蓝图要在之后通过发现、研究或事件解锁。

开局不提供脱离蓝图的通用徒手建造，但也不需要工作台。玩家只能先拾荒、搬运和使用已有物品；找到材料后可以在符合条件的空地或车上空位直接规划基础设施。复杂设施是否可建由研究解锁、材料和支撑面决定，不由某个额外工作台按钮决定。

研究台可以是一张书桌，是可选的研究设施而不是建造前置。居民没有书桌时，可以坐空地、凳子或躺在床上研究；桌上的纸、笔、水杯通过已有 `PlacementRegion` 放置规则表达，提供研究速度、并行人数或复杂研究资格加成。研究台本身的建造仍走普通蓝图事务。

3D 打印机也作为普通设施进入同一套蓝图、放置和生命周期规则，可以建在车辆甲板、永久节点或临时路边空地；它不替代蓝图施工，也不是所有设施的建造前置。打印行动需要电力、打印介质和不可打印的控制芯片，打印完成的零件先进入打印机输出槽或附近可达堆料区，再由居民按普通搬运事务送入设施蓝图。拆除打印机时按设施库存和可回收材料结算，不能把未取出的打印件或芯片凭空传送回车辆。

设施实例需要记录四类生命周期信息：

| 字段 | 语义 |
|---|---|
| `SiteId` | 所在节点、临时停靠点或车辆的稳定身份；没有节点时仍由路线锚点生成稳定临时 id |
| `PersistenceKind` | `PermanentNode`、`TemporaryRoadside`、`VehicleMounted` 或 `Retired` |
| `RouteAnchor` | 临时设施放置时的路线 id 与进度位置；车辆距离由模拟路线进度计算，不读取 Unity 场景距离 |
| `RetentionDistance` | 临时站点离开后还能回访的最大路线距离；超过阈值才提交 `Retired`，不在每帧销毁对象 |

在永久节点中，地面设施、库存、磨损、升级和未完成蓝图归节点存档；在途中停靠点中，设施与地面材料只在 `RetentionDistance` 内保留；车载设施则随车辆移动。玩家出发时必须在“拆除并回收 / 留在这里 / 取消出发”三种意图中选择；留在途中不会把资源传送回车，超过距离后由一次确定性生命周期结算清理。清理前可以给出一次低打扰提示，不能静默吞掉已提交库存。

第一轮只实现一个永久起步节点和一个途中临时停靠点。不要在本轮设计完整的前哨管理、跨区域实时加载或任意荒野物件永久持久化；它们会把一个清晰的设施规则扩大成地图数据库。`NomadWorldItemSaveData`、`PlacementRegion`、蓝图施工暂存区和现有搬运租约已经可以承接材料堆与原地建造，站点生命周期只需在此之上增加持久范围和路线锚点。

## 6. 放下动画与 IK

游戏 System 而不是 Animator Event 拥有物品转移的唯一提交点。推荐次序为：

1. 预留来源、物品和目标区域内的精确姿态；
2. 居民使用与区域或其所属设施关联的 `InteractionSlot` 到位；
3. 播放通用“放下/拿起”动作，手部 IK 对齐预留姿态上的视觉锚点；
4. 在 System 的确定性提交检查点中改变物品 owner/location/pose；
5. 动画收尾并释放预留。

早期可用通用动画 + 单手或双手 IK + 提交帧吸附完成，不需要为每个桌面和每种杯子烘焙一份动画。只有特殊设备或物品明显穿模时再增加设施级修正。

## 7. 蓝图、建材与施工阶段

玩家确认候选建筑后，创建的是蓝图，不是完成设施。蓝图从创建起就占用最终建筑占地，并可声明临时施工/堆料边界，避免后建的东西或通行路线穿过未完工结构。

首版状态机：

```text
Planned
  -> WaitingMaterials
  -> ReadyToBuild
  -> Building
  -> Commissioning
  -> Complete
```

取消、设计失效、支撑面改变或存档恢复会进入明确分支，不把半成品假装成 Complete。建筑配方包含：

- 精确材料及数量，以及可允许的替代材料；
- 标准人力时间（例如标准建造者工作 3 个模拟小时）；
- 建造技能类别、同时工作人数上限、必需和可选工具；
- 不同阶段的材料消耗/可回收规则与启用条件；
- 可选专用阶段视觉，没有时使用通用施工表现。

### 7.1 建材是真实库存

蓝图拥有自己的 `ConstructionStaging` 库存与放置区域。搬运者先预留仓库批次和蓝图剩余需求，把真实材料运到待建区。所有必需材料到齐后，蓝图才进入 `ReadyToBuild`。

视觉不必为每一颗螺丝创建对象。精确数量依然在库存账本中；View 根据已到料的类别和数量档位，显示钢板堆、管材捆、零件箱或卷起的线缆。这保留“物资正在到齐”的可读性，又不让对象数与材料毫升/克数同比增长。

### 7.2 施工视觉可逐步精细化

所有设施先共用一条可用的回退链：

1. 蓝图轮廓/半透明最终体；
2. 真实到料堆；
3. 基础框架、脚手架、防尘布和通用工具道具；
4. 按工时进度显示轮廓/溶解或组件切换；
5. 竣工时原子启用正式设施。

重点设施以后可提供 `foundation / frame / shell / complete` 等专用模型。通用链保证没有专用半成品网格也能完成玩法，专用资产是可替换的表现升级。

## 8. 多人施工不需要无限多手工停靠点

蓝图确认后，System 沿最终占地的可达外周动态生成有限的 `ConstructionWorkPose`：

- 间距根据 NavMesh Agent 半径、蹲姿和工具挥动净空决定；
- 候选点需要能抵达、不与建筑/到料堆相交、不与其他工作姿态重叠；
- 同时施工人数是“配方上限、当前可达工作姿态数、现有工具/人员”的最小值；
- 每个居民仍需要预留自己的姿态，不依赖角色刚体互相推挤。

人力用“已提交工作量”累积，而不是单纯倒计时。每次连续工作片段开始时，根据建造技能、工具、疲劳、照明和环境取样一个稳定效率修正；不逐帧重掷导致进度抖动。多人的输出可相加，但空间狭窄或互相干扰时可有轻微协作折损。

### 8.1 施工者挡路时如何让行

施工是可在安全检查点中断的长任务。开阔区域先交给 NavMesh 局部避让；真实窄口或路径长时无进展时，执行器向低紧迫施工者发出 `YieldRequest`：

1. 施工者在下一个短工作片段结束后停止动画；
2. 提交本片段已完成的工作量，放弃临时工作姿态；
3. 移动到就近安全候等位，通行者通过；
4. 之后重新投标或领取可达工作姿态继续。

首版不做“任何动作在任意动画帧上都能无损中断”；安全检查点已足以表现自然让行，也能维持存档与材料守恒。

## 9. 谁来搬料和施工：全局工作板 + 个人 Utility

完全个人随机决策容易让多人重复搬同一份料、抢同一个工作位；完全中央派工又会把居民变成没有偏好的机械工人。因此采用混合模型：

- `JobBoard` 只发布可领取工作、依赖、希望人数、玩家优先级、等待老化和已领取租约；
- 每个居民根据距离、技能、需求、疲劳、性格偏好、工具可用性、协作倾向和玩家优先级生成 Utility；
- 评分只决定谁想做，原子工作租约保证同一份料/同一工作姿态不被重复领取；
- 中央层不指定“居民 A 必须做”，只管容量、前置条件、飢饿防护、冲突和长时饿死；
- 稍后可允许玩家提高/锁定任务优先级，但不需要玩家逐人下指令。

这个模型表现了居民会协商与分工，同时保留“谁擅长、谁离得近、谁今天不想干”的个体性。

## 10. 工具、保养、修理与清洁共用任务骨架

建造、紧固、清灰、通管、修复漏水都可以共用一条任务骨架：

```text
诊断/领取工作
  -> 预留工作位与目标
  -> 查找必需/可选工具和耗材
  -> 从真实容器取出并携带
  -> 导航至工作位
  -> 按检查点累积工作量
  -> 原子提交结果/消耗品
  -> 归还工具或按规则临时放置
```

工具是真实物品，可能在柜子、抽屉、工具带或另一位居民手中。配方可声明：

- `Required`：没有就不能执行，例如焊接机；
- `OptionalEfficiency`：没有仍可慢速完成，例如用手擦代替拖把；
- `OptionalQuality/Risk`：没有就增加返工、受伤或残留污染风险。

不建立一个包办所有领域的 `WorkComponent`。任务骨架只复用预留、工具获取、工作量、中断检查点和结算事务；建造成果、积灰类型、故障部件和维护消耗仍由各领域定义。

## 11. 支持区域能力，不在底层写死“车前后不能建”

每个支持面暴露能力标签，例如 `VehicleDeck`、`ExteriorGround`、`RoadSurface`、`Roof`、`WetGround`、`HighVibration`。建筑定义声明必需/禁止能力：

- 普通车载设施要求 `VehicleDeck`，还可限制承载、边缘净空或连接口；
- 普通室外房屋要求 `ExteriorGround` 且禁止 `RoadSurface`；
- 路面或坡道反而要求 `RoadSurface` 或可以改写该标签；
- 车辆前后的通行带可通过支持面分区禁止大部分设施，但仍允许路面、支撑板或专用对接件。

这样车外、车内和未来其他基地可共用放置/蓝图/施工骨架，只替换支持能力和配方数据。

## 12. 选中与详情面板

普通模式的点击选中不直接操作 GameObject，而是把视线命中还原为稳定实体 id，通过 Command 更改选中投影。面板只读 Model 投影：

- 设施：名称、功能、库存/端口、等效磨损、维护欠账、污染、当前故障、风险分档、正在排队的任务；
- 蓝图：已到/缺少材料、标准人力时间、已完成工作量、可并行人数、工具要求和阻塞原因；
- 居民：姓名、年龄、性别、特长、爱好、性格/压力反应、当前需求、当前任务、计划和阻塞。

选中状态和详情投影可存在 Model，但面板展开/折叠、滚动位置和高亮等瞬时 UI 状态不需要进入玩家存档。

## 13. 存档与重建真值

存档至少要保存：

- 支撑面/设施的稳定 id，每个已放置物品的 region/slot id 和局部量化姿态；
- 物品稳定 id、占地定义 id、容器/居民/区域所有权、内容与连续状态；
- 蓝图定义 id、姿态、阶段、到料库存、已提交工作量和阶段效果是否已提交；
- 正在进行的搬运/施工任务租约、预留的精确姿态和安全检查点；
- 已经取样的工作片段效率与领域随机游标，读档不重掷。

NavMesh path、当前 IK 权重、溶解材质参数和候选工作姿态列表可从上述真值重建，不写入存档。加载顺序是先验证 id/容量，再重建物品占用和任务租约，最后重算导航与表现。

## 14. 状态的美术表现分层

同一个设施的积灰、老化和故障不应全部用一次简单变色表现：

| 状态 | 优先表现 | 理由 |
|---|---|---|
| 积灰/沙/薄雪 | 共享 Shader Graph/SubGraph + 每实例 `MaterialPropertyBlock` + 顶面/暴露遮罩 | 同一套覆盖多资产，强度连续，不复制整套材质 |
| 长期磨损 | 资产的 Curvature/AO/顶点遮罩 + 掉漆、粗糙、划痕和小法线 | 边缘与接触部磨损与网格相关，纯世界噪声不够可信 |
| 具体故障 | 可切换小部件、漏液/VFX、积水 Decal、火花、摇晃/卡死动画和异音 | 玩家应能从现象判断“哪里坏了”，不只看一根数值条 |
| 严重几何损伤 | 破损部件/模型变体或可拆卸模块 | Shader 无法改变轮廓、孔洞和机械可动性 |

积灰共享 Shader 是合适的第一步，但需要保护区遮罩，避免屏幕、灯光、经常握持的把手和密封内腔同样被均匀覆盖。

## 15. 与 SSFramework 的职责映射

| 层 | 职责 |
|---|---|
| Model | 物品位置/所有权投影、蓝图、工作量、到料、选中实体和可观察阻塞 |
| System | 放置事务、搬运/施工编排、JobBoard、中断检查点、材料/工作量提交 |
| Utility | 无 Unity 依赖的区域几何账本；NavMesh/IK/Animator/Shader 等 Unity 能力由 Mono Utility/Adapter 封装 |
| View | 放置区域与堆料、蓝图/半成品、IK 与动画、状态 Shader/VFX、选中高亮和详情 UI |
| Command | 玩家放置 Zone、确认/取消蓝图、修改优先级、选中实体；不直接改 Renderer 或库存 |

世界放置与施工是《游牧工坊》领域能力，先留在游戏项目。只有第二个真实项目证明某个纯几何或任务原语通用，才考虑下沉 Framework；不因为名字看起来通用就提前扩大框架。

## 16. 分期实施与 Harness

### Phase A：先修复水罐的空间真值

**进度：已完成首轮实现与自动化/视觉验证。** 后续只有试玩或 Phase B 暴露出几何契约缺口时才回补，不继续横向扩张。

1. 在无 Unity 依赖的 Simulation 中建立有向矩形 `PlacementRegionLedger`；
2. 锁定包含、重叠、方向候选、稳定选位、预留/提交/取消和存档往返；
3. 车辆水箱与饮水站定义可观察水罐停放区，建造预览把该区域纳入功能净空；
4. 水罐返还时保存精确 region/pose，不再由 View 猜侧偏移；
5. 回归施工紧邻、45 度旋转、任务中改道、存取和水守恒。

### Phase B：一只杯子与一片台面

**进度：首条原子拿放闭环已完成；正式动画/IK 与玩法动机尚未完成。**

- [x] 台面 Authoring 区域 + 数据驱动杯子 footprint；
- [x] 两种不同尺寸 footprint 的共存容量、越界/重叠反例与任意朝向；
- [x] Model / View / 开发诊断投影，以及存档后完全相同的局部姿态恢复；
- [x] 来源恢复位与目标姿态的联合预留、拿起/携带/放下原子提交；
- [x] 携带投影、通用右手锚点和取消/检查点精确回滚；
- [ ] 正式 Humanoid 拿放动画、手部 IK 与设施接触修正；
- [ ] 由饮水、清洁或整理等上下文产生真实拿放意图，而不是开发 Harness 按钮。

### Phase C：一座真实蓝图

- 选择既有饮水站或一个更小设施，把“确认即建成”替换为蓝图；
- 一种建材、一个真实搬运批次、一种工具和一名施工者；
- 到料堆、通用脚手架/半成品、标准工时与技能修正；
- 建造中暂停、取消、存档/加载和材料守恒。

### Phase D：多人、让行与维护工具

- 2–4 名居民对同一蓝图的工作姿态生成、租约和人力合并；
- 窄口通行的施工让行与无进展诊断；
- 水箱实体维修包的取得、到位工作和原子消耗已经实现；仍需把保养转成真实劳动，并补工具与备件补给，不重做现有 Use Lease。

### 每个阶段的停止条件

- 几何账本可用纯 C# 测试重现，不需要启动场景猜错；
- 没有一件物品同时在容器、居民手中和区域三处；
- 存档/取消/导航失败后没有泄漏预留或重复提交；
- 开发视图可显示 region、footprint、候选姿态、工作位和阻塞原因；
- 实际 Game View 确认没有明显穿模，又不把单帧截图当成长时任务已经成立的唯一证据。

## 17. 本轮明确不做

- 不在第一次迁移中同时实现堆叠物理、自动整理、任意多边形表面和整个餐饮系统；
- 不使用实时刚体模拟作为物品最终位置真值；
- 不为每一座建筑手工制作数十个施工停靠点；
- 不把建造/修理/清洁的领域结果塞进一个万能工作组件；
- 不在第一版就要求每座设施都有专用百分比施工模型和专属动画；
- 不会因为文档已写就禁止试玩后修改；若规则产生无趣的家务微操或不值得的复杂度，优先自动化、合并或删除。
