# 《游牧工坊》连续建造、导航与设施交互设计

> 状态：**三居民原生移动、身体约束与玩家检查点 v0.13**，更新于 2026-09-05。正式 Foundation 已接入共享世界和每人拥有的 NavMeshAgent，当前六项原生定向已覆盖 CharacterController 身体约束、实际让位、两个 Seed 往返及旅途存读档；完整 Foundation 回归 100/100，正式 1× 存读档续玩与限制见三居民接线。同步 Soak 明确为角点快进，不能提供原生避让证据。近期按[Foundation](nomad-workshop-foundation-vertical-slice.md)的玩家存档与续玩边界推进；旧格子算法只留作独立纯 C# 回归。

2026-09-06 范围更新：当前实现与上述测试仍是单层正式场景。用户已提出局部上层、梯子与切层，现有连续姿态/分层账本可保留，高度解析、跨层动作和拓扑事务需要扩展；方案与证据见[可扩建甲板设计](nomad-workshop-expandable-decks-design.md)。

## 1. 当前决定

《游牧工坊》的正式方向采用四层分工：

1. **连续建造真值**：设施保存车辆局部平面上的连续位置、旋转和简化占地形状，不再以整数格作为玩法身份。
2. **可选吸附辅助**：可视网格、位置步长、角度步长、边缘磁吸和连接口对齐只帮助玩家操作，均可调整或临时关闭。
3. **连续导航与局部避让**：车辆甲板使用 Unity AI Navigation 的 NavMesh 求几何路径，并由 NavMeshAgent 的局部避让处理空旷区域中的自然会车。
4. **显式交互与交通契约**：设施停靠位、工作位、门口、梯子和其他窄口由游戏自己的预留与行动系统管理；NavMesh 不负责判断“谁有权使用柜门”或何时转移物品。

这不是“所有东西都交给 NavMesh”。NavMesh 只回答角色在几何空间里如何走；建造合法性、设施能力、库存、任务、交互位占用、动作结算和存档仍是游戏真值。

## 2. 为什么不继续让角色沿格线走

整数格很适合快速判断占格与连通，但把搜索节点中心直接当移动轨迹，会人为限制方向。空旷甲板上从 A 到 B 应接近直线，只有遇到设施、甲板边缘或其他居民时才改变方向。

可选的纯网格改良包括八方向 A*、路径可视线简化和 Theta*。它们能解决单人路径折线问题，但仍需要额外实现角色半径、任意旋转障碍、斜边、动态人群避让和局部路径走廊。对本项目这种 3D、自由摆放、预计 10–20 名居民的场景，继续扩写自研导航会与 Unity 已有能力重复。

Unity NavMesh 把可行走空间表示为相邻凸多边形，在多边形图上寻找路径走廊，再朝当前可见拐角行进；空旷区域自然只留下起终点。NavMeshAgent 还包含基于速度的局部人群避让。工程已安装并锁定官方 `com.unity.ai.navigation@2.0.14`，获得 `NavMeshSurface`、运行时更新、Modifier 与 Link 等高层组件；旧的底层 `com.unity.modules.ai` 仍由 Unity 保留。

当前 Humanoid 导航类型使用 `Agent Radius = 0.2 m`、`Height = 1.8 m`，甲板 Surface 覆写 `Voxel Size = 0.09 m`。Unity Inspector 中这个 0.2 m 字段是**半径**而不是完整宽度，因此烘焙净空对应约 0.4 m 的身体直径；这比把 0.2 m 当总宽度更不容易让居民穿过视觉上不合理的窄缝。预览与已提交路径均从这份 Build Settings 读取半径，不再维护另一套手写尺寸。

- [AI Navigation 2.0.14 Registry 元数据](https://packages.unity.com/com.unity.ai.navigation)
- [NavMesh Surface 组件](https://docs.unity3d.com/Packages/com.unity.ai.navigation@2.0/manual/NavMeshSurface.html)
- [Unity 导航系统内部工作方式](https://docs.unity3d.com/2018.3/Documentation/Manual/nav-InnerWorkings.html)
- [NavMeshAgent 与其他组件协作](https://docs.unity3d.com/2021.3/Documentation/Manual/nav-MixingComponents.html)

### 首轮隔离证据

[`NavigationInteractionSpike.unity`](../Assets/Game/NomadWorkshop/Scenes/NavigationInteractionSpike.unity) 已通过同一个 Framework Context 组合：

- `DeckNavigationUtility : MonoUtilityBase` 只封装 `NavMeshSurface`、Agent、路径查询和 Docking；
- `NomadNavigationSpikeSystem : MonoSystemBase` 拥有阶段、交互组预留与真实库存交接；
- `NomadNavigationSpikeModel : MonoModelBase` 把路径比、Slot、争用、物品位置和阻塞原因投影到 Inspector；
- `NomadNavigationSpikeView : MonoViewBase` 只经查询 Command 订阅读模型，派生门、手持物、路径线和调试面板。

一次代表性运行得到：空旷路径长度比 `1.000`、2 个路径点；穿过 27° 旋转柜体的探针长度比 `1.058`、5 个路径点；两居民相向通过时最小间距约 `0.69 m`；A / B 从相反方向分别选择 `right / left` 候选位。两人共享容量 1 的柜门组，居民 B 在 A 接近时和“已经交接物品但仍在关门”时都不能取得预留，最终两件真实物品分别进入两人的独立库存。

这轮还锁定了三个生成边界：玩法根节点不能继承缩放 Mesh 的非均匀 Scale；`MaterialPropertyBlock` 不会随场景保存，期望色必须有可序列化来源再由 View 创建材质；资源提交释放自己的租约不等于设施门口可以立即让给下一人，InteractionGroup 租约必须覆盖完整开门—交接—关门周期。

## 3. 连续设施姿态与可选吸附

设施存档真值改为 `DeckPose`：

- 车辆甲板局部 X / Z；
- 绕甲板法线的 Yaw；
- 稳定设施实例 id 与定义 id；
- 必要时记录所在甲板层或区域 id。

“自由”不等于保存不可控的浮点噪声。`Simulation/DeckPose` 用毫米位置与 0.1° 朝向表达不可变业务姿态；`Simulation/Persistence/QuantizedDeckPose` 是与它可无损往返的可变 JSON DTO，Unity Adapter 只负责转换 `Vector3 / Quaternion`。正式 Foundation 的设施记录、幽灵、交互位和导航障碍现已共用这个真值。

`DeckPlacementSnapSettings` 已实现平移与旋转的独立吸附，底层仍允许设为 0 以支持无级编辑；正式 Foundation UI 当前提供自由、0.2 / 0.3 / 0.4 / 0.6 m 与默认 45° 旋转。非零档位都以甲板原点为共同原点，并是内部 0.1 m 基础格的整数倍；这保证没有原点 / 浮点漂移，但不同粗网格不是彼此的严格子集。吸附只生成新的候选 `DeckPose`，不进入碰撞规则、设施身份或存档格式；可视网格使用当前平移步长重建，因此视觉辅助与实际落点一致。自由模式不吸附且自动隐藏网格，切换档位不移动既有设施。

玩家侧吸附设置与真值独立：

| 辅助项 | 推荐默认值 | 可选行为 |
|---|---:|---|
| 平移网格 | 0.2 m | Foundation UI：自由、0.2 / 0.3 / 0.4 / 0.6 m；非零档位共用 0.1 m 基础格和原点 |
| 旋转吸附 | 45° | Foundation UI 可循环既有角度档；底层支持无级旋转 |
| 边缘磁吸 | 待实现 | 目标是对齐附近设施边、墙边和通道边，可关闭 |
| 连接口吸附 | 条件触发 | 管道、电缆、模块接口进入捕获范围时优先精确对接 |

固定视角和狭小平台容易因完全随意的角度显得凌乱，因此默认开启较细吸附；玩家需要斜放家具或利用边角空间时可以暂时关闭。连接口有机械约束时，接口对齐可以覆盖普通网格设置。

## 4. 不依赖格子的占地与建造验证

每种设施声明一个简化的 2D 占地，而不是拿高模 Mesh 或 Renderer Bounds 直接判定：

- 一个或多个有向矩形、圆或凸多边形；
- 与甲板边界的包含关系；
- 与其他设施占地的间距；
- 维护、开门和交互需要的可选净空区；
- 生成 NavMesh 构建几何所需的简化 Collider。

首版纯内核 `ContinuousFacilityPlacementLedger` 刻意只实现一个或多个有向矩形：它已经支持任意 0.1° 朝向、复合 / L 形占地、多甲板层、稳定实例 id、按 id 排序快照，以及“全部检查通过后才提交”的原子语义。有向矩形使用分离轴定理检查真实相交，刚好接触甲板边或另一个占地允许通过；设施需要视觉缝隙或维护空间时应把相应矩形扩张，而不是依赖不可控浮点误差。圆和凸多边形等形状等真实设施证明矩形近似不足后再添加，避免过早维护通用碰撞库。

快速预览阶段先做确定、便宜的几何检查：越界、占地相交、连接口约束和候选交互位的基本净空。越界和真实占地重叠是硬失败。几何通过后，当前 `ContinuousDeckReachabilityProbe` 把小型甲板按 0.1 m 采样，按 NavMesh Agent 半径与有效 Voxel 扩张新旧有向矩形，并从居民当前连通区执行八方向 Flood Fill。Slot 映射半径收紧为 75 mm，且每个 Slot 还会对候选与既有连续 Footprint 做精确居民净空检查；候选覆盖居民时，起点先迁到最近未阻塞采样点，居民不再占用建造位。

预演会重算候选和每座既有设施的所有 InteractionGroup / Slot。一个 Group 只要有任一备选 Slot 可达就可使用；无任何可达 Slot 才是该功能不可达。这类问题不再拒绝确认，而是作为玩家可以通过搬移、拆除或补建通道修复的运行状态。采样缓冲和设施列表复用，拖动幽灵仍不每帧重建 NavMesh。

这一预检刻意保守；按当前 0.2 m Agent 半径、0.09 m Voxel 和甲板尺寸共 8,320 个复用采样格。调试面板公开本次耗时、访问格数和可达 Slot 数，便于用证据调整分辨率与净空。它只负责提前发现明显死位，确认后的 Unity NavMesh 事务继续处理真实多边形边界与端点采样差异。

正式 Foundation 的当前确认已采用可回滚的导航更新：

```text
几何合法的幽灵（绿 / 橙 / 红可达提示均可）
  → 创建尚未进入已提交真值的候选障碍
  → 把候选设施加入导航构建输入
  → 异步更新小型甲板 NavMesh
  → 更新成功才原子提交设施，并将居民迁到最近可站立 NavMesh 点
  → 从实际 NavMesh 重算已提交设施的 Group / Slot 访问投影
  → 取消 / 复位 / 异常则停用输入并用第二次异步更新恢复导航数据
```

`NavMeshSurface.UpdateNavMesh` 会异步更新变化区域。车辆甲板很小且建造确认频率低，当前实现使用确认后更新，没有为同一类静态设施再维护 carving 双路径：

- 已建成、长期静止的设施进入 Surface 构建输入；
- 玩家拖动的幽灵不进入正式 NavMesh；
- 物理推动的临时箱子等动态物体才使用 `NavMeshObstacle` 局部避让或 carving；
- 导航更新事务期间暂停模拟推进，已有角色停在上一个安全位置；
- 当前版本诊断已建设施的操作 Slot；引入蓝图后，还必须在实体障碍启用前提示并跟踪施工位可达性。

如果实测增量更新仍有明显卡顿，再比较简化 Box carving；不提前为尚未出现的性能问题维护两套实现。

## 5. 交互组与候选停靠位

一个“设施能否使用”不能只看设施 Transform，也不能只存一个目的点。目标结构是：

```text
Facility
  └─ InteractionGroup（一个能力或一个争用资源）
       ├─ Slot A（候选站姿）
       ├─ Slot B（候选站姿）
       └─ Slot C（候选站姿）
```

`InteractionGroup` 负责：

- 稳定 group id，例如 `storage-door-left`、`counter-prep`、`repair-panel`；
- 支持的行动标签；
- 这些 Slot 是“互斥候选”还是“可同时工作的独立容量”；
- 预留 key、队列规则和是否属于设施正常运转的必需入口。

每个 `InteractionSlot` 负责：

- 稳定 slot id；
- 精确站立位置与朝向；
- NavMesh 接近容差和最终贴靠容差；
- 姿态语义，例如腰高取物、头顶取物、跪姿维修或坐下；
- 主手、副手、注视点和物品交接点；
- 对应的交互动作 Profile 与设施执行器提示。

柜门前设置三个点是合理的，但通常应当是同一个门组的三个**备选站姿**，共享容量 1。系统从可达且未预留的点中按路径代价、转身幅度和拥挤代价选最优点；不能因为有三个点就让三个人同时伸手穿过同一扇门。长操作台可以定义三个真正独立的工作组，从而允许多人并行。

复合设施不能把所有站位压成一个可达布尔值。一座厨房可以同时有 `cooktop`、`storage-door` 和 `water-port` 等独立 Group：灶台可用不代表柜子可用。`FoundationFacilityAccessState` 因此保留扁平 Slot 位掩码，System 按 Group 归约为 `Reachable / PartiallyReachable / Unreachable`，View 再按定义中的稳定顺序展开每个停靠位。

### 可达性的玩家表达

- **建造视图**：不依赖悬停，始终展开所有设施的全部 Slot；可达为绿，不可达为红。部分 Group 失效时整体持续橙色，所有 Group 失效时整体持续红色；每个没有可达 Slot 的 Group 在候选位中心保留独立红色功能警示。
- **非建造视图**：当前不对整栋模型常驻染红。推荐下一版用小型状态图标 + 可点击警报列表，选中时才显示详细 Slot；这样既能告警，又不会长时间破坏正式美术。

仅 `NavMesh.SamplePosition` 成功还不够。候选 Slot 最终需要同时满足：

1. 位于正确 NavMesh 上；
2. 从当前居民位置存在 `PathComplete`；
3. 居民胶囊在最终姿态不与设施或他人重叠；
4. 目标在当前动作 Profile 的 IK 可达范围内；
5. InteractionGroup 预留成功。

角色先导航到 Slot 的接近区，再进入短暂 `Docking` 阶段，平滑对齐精确位置和朝向；只有对齐完成才开始开门、伸手和物品交接。

## 6. 动画到底属于人还是设施

不能全部绑定在一边。正确拆分是：

| 所有者 | 内容 |
|---|---|
| 居民表现 | 走路、站立、伸手、弯腰、跪下、搬运等 Humanoid 动画；不同体型可把同一语义映射到不同 Clip |
| 设施表现 | 柜门转轴、抽屉滑轨、阀门、按钮、机器运转状态；简单门优先由参数化执行器驱动，不必每扇门制作独立 Clip |
| Interaction Profile | 编排居民动作语义、IK 权重曲线、设施执行器时刻、音效/VFX 和物品挂点切换 |
| 游戏 System | 预留、取消、库存转移、失败恢复和最终结算；动画不是业务真值 |

一次“从柜中取货”的目标时序是：

```text
预留柜门组与货物
  → 选择可达 Slot
  → NavMesh 导航
  → Docking 对齐
  → 居民播放 ReachWaist / ReachHigh 语义
  → 设施执行器开门
  → 在确定性交接标记把物品从柜内库存移到居民携带库存
  → 物品视觉挂到手部 Socket
  → 收手、关门、释放 Slot
```

Animator Event 可以触发表现提示，但不能成为唯一库存结算入口；动作被跳过、加速、切出画面或取消时，System 仍必须得到确定结果。项目现有 `FacilityInteractionAnchor` 已有站位、动作语义和单手目标，可作为迁移来源，但其单锚点结构不直接扩张为最终 API。

## 7. 多居民拥挤

NavMeshAgent 的局部避让适合处理开阔区域里的绕行、减速和自然会车，但它不是任务队列或全局死锁证明。目标组合为：

- NavMesh 路径走廊负责绕静态设施；
- NavMeshAgent 局部避让负责居民之间的短程速度调整；
- InteractionGroup 在出发前预留最终工作位，避免所有人挤向同一点；
- 门、梯子、单格桥和其他真正的窄口使用显式通行 token；
- 长时间离目标无进展时，保留资源所有权并重寻路，让软占位居民实际走开；
- 任务紧迫性由业务调度决定，不直接映射为更高避让优先级：Unity 高优先级 Agent 会忽略低优先级 Agent，不能保证身体互避；
- 居民之间不使用非 Kinematic Rigidbody 互推，避免与 NavMeshAgent 同时争夺 Transform。

休闲散步和原地发呆属于**可抢占软占位**，不会取得设施 `InteractionSpace` 的硬租约。当前三居民执行器发现附近闲人阻挡目标时，会为没有资源/空间租约的闲人选择可达空地，让其实际走开。散步及尚未开始的爱好连续 3 秒无进展则释放自己的可选活动并重新决策，不取消他人工作，不发放未完成的休闲收益。固定座椅、床位等本身有容量的活动仍需对应 Group 租约。普通走路与末段停靠都经 CharacterController 约束；初始化、恢复/建造迁移和显式快进后同步才迁移身体位置，内部 Agent 可重新锚定到同一脚底，停靠净空和容差见 [Foundation §4](nomad-workshop-foundation-vertical-slice.md#4-寻路与多人交通契约)。

建造后的路线恢复以语义而非旧坐标为真值：`FoundationResidentMoveIntent` 保存任务阶段、设施功能、首选设施与替代政策；提交新障碍后先重选原设施 Slot，再选择最近同功能设施，暂时失败则进入 `WaitingForRoute` 限频重试。设施交互路径使用约半个 Voxel 的窄 NavMesh 端点容差，并在末段精确走到量化 Slot 位置和朝向；任意空地散步才使用较宽松的通用采样。

因此正式方案不对整个甲板逐格预留。只有具有真实容量语义的地点才离散化：工作位、门口、梯子、座位和队列点。三人 Adapter 当前使用 High Quality，全体行走者使用相同优先级 50、静止时使用优先级 0；这只是当前小人口配置，没有 20 人或目标设备性能结论。窄口通行政策待正式任务需要时再实现，不能把局部避让当作一般死锁求解器。

## 8. 与 SSFramework 的职责映射

| 层 | 目标职责 |
|---|---|
| `NomadFoundationModel` | 世界设施、建造/旅途投影及独立个人记录；不持有原生 Agent |
| `NomadFoundationSystem` 的建造事务 | 自由摆放硬几何验证、提交/取消回滚、导航更新与可修复可达投影 |
| `DeckNavigationUtility : MonoUtilityBase` | 封装 `NavMeshSurface`、路径查询、增量更新与 Unity 状态，不决定任务 |
| System 的个人执行对象 + `DeckResidentMotor` | 前者拥有任务/目的地/租约；后者拥有 Agent、停靠位置与物理生命周期，System 读取进展并发布 Model |
| System + `FoundationInteractionSpaceRuntime` | 功能组/工作位选择、个人空间租约、动作阶段与结算；不要求额外创建同名 System 层 |
| 存档 Command + `IStorageUtility` | 校验版本化整档并原子写入；不直接知道 NavMesh、Renderer 或动画对象 |
| View | 显示网格/磁吸/幽灵/路径与动画，只订阅读模型并发送 Command |

NavMeshAgent 的位置允许有帧率差异；库存、任务所有权和结算不能依赖一次身体接触的先后顺序。当前 v9 存档包含量化姿态、多居民连续状态和随机游标、设施/物品/实例库存，以及有限旅途与地点。半途行动按各自已提交边界保存，加载重新寻路和建立个人租约，不序列化 Unity 路径走廊。Framework Command + `IStorageUtility` 已证明文件往返，玩家可用的保存/读取反馈与异步世界所有权仍是下一步。

自定义模拟倍率需要单独验证：正式 1×–4×可以按倍率调整 Agent 速度、加速度和 Animator；16× 自动测试不强求复现视觉避让，应通过可替换导航 Adapter 或测试模式快速完成路线，避免让测试依赖墙钟和 RVO 帧序。

## 9. 分阶段迁移与删除边界

1. **已完成导航基线**：安装并锁定 AI Navigation 2.0.14；隔离 Harness 已验证空旷直线、绕 27° Box、两个 Agent 会车和运行时同步构建。
2. **已完成连续 Foundation 迁移**：Model / System / View 共用 `DeckPose + ContinuousFacilityFootprint`，位置 / 旋转吸附可独立关闭，正式场景不再读取 `DeckCell + QuarterTurn`。
3. **已完成建造导航更新**：几何合法的候选障碍经异步 `UpdateNavMesh` 后原子提交；不可达保留为可修复状态，取消 / 复位 / 异常才停用候选并二次更新回滚。
4. **已完成实时预演与建造取证**：纯 C# 采样连通图随候选姿态更新，居民可迁移；新旧设施按 Group / Slot 诊断，建造视图持续标记异常设施并支持悬停展开。
5. **已完成运行检查点**：设施、实例饮水/厕所库存、多居民身心、世界物品、随机游标、设施风险和首段有限旅途已经能捕获、原子落盘并重建。半途资源/物品租约回到守恒业务边界；蓝图和没有恢复语义的行动状态仍明确拒绝，不伪装成完整动画续接。
6. **已完成放置区与首条拿放**：水罐、杯具与维修包均消费同一放置账本。下一份消费者优先来自旅途补给 / 部署，不把完整蓝图作为启程前置条件。后续蓝图仍遵循[世界物品放置与蓝图施工设计](nomad-workshop-world-placement-and-construction.md)的材料、施工与取消契约。
7. **三居民原生移动已接线**：个人执行对象持有实际 Agent，导航 Utility 创建并配置，View 只消费位置投影。暂停/取消/读档/建造、共享饮水、让位和两个 Seed 的有限停靠往返已通过实际帧回归，完整证据见[三居民 C](nomad-workshop-three-residents.md)。10–20 人及任意窄口仍待后续压力 Harness，不改变当前三人产品目标。
8. **删除边界**：旧格子算法当前只留作独立纯 C# 回归；若它们不再保护任何真实边界，连同测试删除，避免两套真值。

当前仍不同时制作正式 UI、复杂 Root Motion、全身 IK、门口队列、跨甲板楼梯和所有设施动作。已有隔离 Harness 先保护一扇柜门、三候选位和两名居民的危险接缝。

## 10. 验收状态

- 空旷甲板上居民路径接近起终点直线，不再沿可视网格折行；
- 任意角度放置一个矩形设施后，居民能自然绕行且不穿模；
- 平移吸附和旋转吸附可分别修改或关闭，关闭后保存/加载姿态仍稳定；
- 一个 InteractionGroup 的多个候选 Slot 中任一个可达即可使用；复合设施的每个 Group 独立判定，不因另一功能可用就掩盖当前功能失效；
- 候选设施拖动时实时显示交互位可达性；可达性异常给出明确警告但仍可建造，越界或占地重叠才禁止确认；
- 建造视图中不悬停就能看见所有设施的全部 Slot 与异常标色；新候选恶化既有设施时，既有设施在确认前就更新状态；
- 两名居民不会领取同一个容量 1 的柜门组，开阔区域能够互相避让；
- 一次取货只发生一次真实库存转移，取消前、开门后和交接后都有明确恢复语义；
- 前七项由正式 Foundation 与两人隔离 Harness 分担验证；正式三人共享资源/工作位、原生 Agent 与安全检查点已有回归，玩家存档 UI、蓝图和半途动作续接尚未完成；
- **未完成** 20 人压力测试；尚无到达率、最长无进展时间、目标设备帧耗和避让质量数据。
