# 游牧工坊：可扩建甲板、多层建造与表现衔接

> 2026-09-06，可行性方案，尚未实现。用户确认发展方向为小甲板起步、逐渐外扩、允许局部上层和围护部件；提出最多三四层。本文记录代码证据、建议方案和阶段验收，不把概念图或已有 `DeckLevel` 字段当作多层已经可玩。唯一近期开发队列仍在 [Foundation §9](nomad-workshop-foundation-vertical-slice.md#9-近期队列美术样板与可扩建建造)。

“初期四分之一”指上轮大平台的**面积**约四分之一，而不是宽和长各缩至四分之一。概念可用 10 × 7 m 对比 20 × 14 m；正式尺寸以三人生活设施、身体净空和施工通路实际排布为准。模型保持米制尺寸，不整体缩小人物和设备凑布局。上层暂以 0–3 的层编号、最多四层作为可配置验证目标，首先只验证两层；不是立即承诺四层内容。

## 3. 甲板外扩与轮组

### 3.1 主车架与地板分开

建议采用“主车架承载 + 局部外挑”，而不是沿每个甲板外角自动生成轮子：

- 主车架保存稳定原点、承载等级和有限轮组/履带安装点。概念图继续用履带，实际资产可替换为轮组，安装点契约相同。
- 小型扩建板连接已有结构边或梁，下面能看见托梁；凹凸轮廓不改变全部轮组位置。
- 大规模扩建需要升级车架段、承载或增加一组对称轮组。展示升级前后的承载、外挑范围和可用面积，不在每次加板时重排底盘。
- 车架升级保持既有坐标原点与实例姿态，不因重新居中导致全部设施、人物和存档漂移；相机可以使用派生包围盒重新取景。

初版用承载预算、最大外挑距离、支撑连通和层数限制表达工程取舍，参数需在样板中校准。上层结构、设施与库存质量计入总载荷；重设备可限制在主车架或加强区。初版不模拟连续结构应力、任意倒塌和车体刚体侧翻；玩家的超限建造给出具体原因。是否进一步模拟侧向失衡留到实际玩法需要时决定，不能用这一简化宣称真实机械安全。

### 3.2 非矩形区域和自由摆放

静态覆盖输入、原生通行与三居民场景的阶段实现见 [NW13 局部甲板样板](nomad-workshop-deck-support-spike.md)；正式材料施工与结构存档仍按下文 S1 推进。

建议结构板采用统一尺寸与结构边吸附，设施继续保持现有自由位置/旋转。这是两种 Authoring 操作，不把装饰网格升级为所有玩法的硬格子。

结构真值为有稳定 id 的楼板/梁/连接件及其挂接关系，按楼层派生“板片并集减去孔洞”的支撑区域。比较任意多边形直接编辑与模块板片两种方案：前者自由度高但拓扑、UV 和操作复杂，后者更适合本轮 AI 成组模型、增量扩建和确定性验证；先选后者作为实现建议。保持毫米精度，具体板长/宽/层高随首批样板验证冻结，不在程序多处硬编码。

空间判定需完整覆盖设施占地和必要净空，不能只看设施中心、四个角或大包围盒。凹边、孔洞与跨板缝必须通过区域差集/覆盖判定；占地横跨两个相邻板是允许的，横跨无地板孔洞是硬失败。邻接板边只生成一份外沿栏杆/封边，连续碰撞输入消除板缝毛刺。上层的局部板也按同一规则处理。

拆板、拆柱或拆梯先检查居民、物品、设施、上层支撑及正在使用的通路。初版拒绝会悬空、困住正在通行者或破坏依赖的拆除，并展示依赖对象；由玩家先搬迁/拆除上部。暂不自动连锁拆除，更不把已投入物资直接消失。结构缺支撑与设施暂不可达是不同失败：保留已有“可建但暂不可达”的警告语义，不一律变成禁止建造。

## 4. 多层、梯子和施工

楼层目录负责稳定层 id、地板高度、结构厚度和有效支撑面。设施放置、槽位、物品区域、居民脚底、导航障碍与鼠标拾取都经这个目录解析；不能由各 View 自行乘一个层高。车外停靠地面继续有独立空间身份，不因为高度相近被归为第一层甲板。

分层隔离只解决普通平面占地，不能允许高水箱或烟囱穿过上层楼板。构件/设施还需声明高度区间与必要操作体积，用“水平占地交叠 + 高度区间交叠”检查楼板、梁、棚顶和跨层设备；人行区域检查实际净高。先采用分段棱柱体，不为这一需求引入完整体素世界。未覆盖区域可以向上伸出设备，后续补板时则必须避开它或先搬迁。

导航方案先比较“一个三维 Surface 包含全车”和“按楼层管理 Surface + 显式连接”。建议以按层输入/修订管理为目标，先用两层 Harness 检验重建成本与连接可靠性，再固定 Adapter 内部划分。两种方案都保留原生 NavMesh 平层行走，楼层号不能仅靠最近 Y 猜测。Unity 的 [NavMesh Link](https://docs.unity3d.com/Packages/com.unity.ai.navigation@2.0/manual/NavMeshLink.html) 可连接同一种 Agent 的不同 NavMesh；它提供几何连接，梯子容量、携物政策和攀爬动作仍由游戏负责。

推荐梯子闭环：等待入口 → 预留梯子和出口落脚区 → 到入口 → 攀爬 → 验证出口并落脚 → 释放。初期一架梯子一次一人，双向按稳定队列避免对顶；正常走路时仍使用现有局部避让。上下口、头顶净空、扶手和开孔都在构件定义中明确；不让整张楼板从梯子顶部穿过去。

攀爬位置由逻辑移动阶段驱动，动画跟随；一旦进入攀爬，业务取消在有效落脚点收口，暂停则冻结。预留期间禁止移走相关梯子/支撑。随身小物可以背挂，手提水罐或大材料的通过能力要由搬运规则判断；首个两层样板可只允许空手/背负小物上梯，大物资需要楼梯、吊运设施或分包，不能让角色双手抱大箱子同时爬梯。

同 X/Z 的另一层不构成到达。所有取水、维修、驾驶等动作，在资源结算前都要验证目标楼层、实际脚底高度及 Slot 租约。Unity [SamplePosition](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/AI.NavMesh.SamplePosition.html) 不检查遮挡，可能采到另一层，所以采样必须受目标层/高度容差约束，失败时保留明确不可达状态。

施工保持“玩家蓝图 → 到得了的施工位 → 真实材料与工时 → 结构提交”。第一块外挑板可从旧甲板边施工；第一块上层板从低层可达施工位搭建柱/梁，再建梯子和上层入口板，最后允许居民上去扩建。上层不可达不妨碍从下方可达工作位施工，但不能出现必须先站在尚不存在的楼板上才能建出该楼板的循环。先复用现有事务验证即时结构提交，正式施工只实现这一条真实材料链，不等待完整通用蓝图系统。

## 5. 围护部件如何建造

| 部件 | 放置与连接 | 规则及表现 |
|---|---|---|
| 底部/底盘 | 主车架接口，车架段与安装点 | 拥有承载与轮组配置；上表面若可走，显式生成支撑面，装饰底壳本身不产生地板 |
| 楼板/甲板 | 结构边或梁，局部增加，允许留孔 | 支撑/可走/是否挡雨分开定义；封闭板与格栅不同，不能默认任何上层地板都防水 |
| 梁柱 | 柱脚与梁端接口 | 支撑路径、占地和高度净空，展示真实连接；超跨度先拒绝而非自动隐藏柱子 |
| 外墙/内部隔墙 | 楼板上的连续墙段，结构吸附可辅助 | 使用实际厚度碰撞；内部隔墙也能划分房间，与同位置外墙不重复收费/占据 |
| 门 | 墙段上的开口区间、门框及铰链 | 门洞是真洞；扇叶分件，逻辑开闭/权限/阻塞决定通行，动画跟随。开门弧和等待区需净空 |
| 窗/玻璃 | 墙洞中的独立框与玻璃 | 透明并不等于可走或不挡风雨；封闭窗、可开窗、破损窗的透雨/通风另有属性 |
| 顶棚/屋顶 | 墙顶或柱梁支撑，允许只覆盖部分 | 形成覆盖区域；雨棚侧面仍开放。屋顶不默认可站立，上人需具备楼板承载/通行能力 |
| 梯子/楼梯/舱口 | 两个层级落脚区和必要开孔 | 两端、容量、通行条件、可携物种类明确；舱口开关与通行连通同一事务更新 |

墙采用稳定墙段和其上的开口区间，门窗保存宿主墙段 id 与开口位置；相同边通过规范化端点避免生成双墙。墙可先限直线和标准长度，后续再支持斜墙；仍不改变设施自由旋转。门窗替换须检查开口重叠与上方支撑，不能只换外观材质。

同一构件定义同时提供规则几何、支撑/开口接口、物理输入、可见模型和动作 Pivot；由同一提交结果分别派生，而非从高模三角形反推支撑或遮雨。程序生成可变长度板/梁/墙体与重复框架，Blender 制作固定高辨识度设施、连接件和分件门窗；共享材质与接缝规格防止扩建后每块板像不同游戏的资产。

## 6. 切层、玻璃、天气和材质

选择第 N 层时，主要显示该层人物/设施；更高层的遮挡渲染隐藏，当前层屋顶自动剖开，近侧墙可降为矮墙/截面。较低层通过当前层孔洞可见，保留结构支撑的必要视觉线索；另提供完整外观模式看整车。初版优先硬切配合短过渡，半透明叠三四层容易变灰且选择困难。

隐藏仅作用于 Renderer、阴影策略和当前可选对象集合，不停用持有模拟、Collider、NavMesh、雨水覆盖或任务的父对象。切层后地板仍承载、屋顶仍挡雨、居民仍在其他层工作。拾取先选楼层，再在该层有限有效区域/部件上命中；建造孔洞或无板位置时显示无支撑失败，不穿透选中低层物体。各层 UI 以层号、任务提示和少量轮廓标记表示看不见的人，不把所有人叠在一起。

玻璃单独材质槽和网格，先做轻微着色、可读窗框与克制反光；从实机验证排序、阴影和室内曝光。美术隐藏与业务“窗户打开”是两件事。镜头切入室内不把全画面曝光拉爆，甲板维持中明度灰褐色，人物和设施用局部色差、轮廓、清楚操作件提高辨认。

静态旧漆和使用痕迹属于材质底色；新增积灰、潮湿、积水或故障状态由业务投影控制材质/粒子。先做直接竖向雨覆盖：已建成完好的顶棚或防水楼板减少下方受雨，孔洞、损坏和侧开口分别处理。再做由墙段/门窗围成的简化房间连通与密闭程度，区分“有雨棚”与“封闭房间”，不能仅凭头顶有板就完全免疫沙尘。

雨水第一条可玩链采用按板片/区域积水体积与固定步结算：降雨 × 暴露面积 → 积水 → 排水口外排或收集容器 → 蒸发。开边排水与封闭低洼板不同，水的输出有去向；屋顶排水不能凭空消失或计入两次。暂不做三维流体与连续坡面水力求解。施工、开关门窗或破损改变覆盖时，先按旧暴露结算到当前 Tick，再应用新覆盖，防止一次建棚抹掉此前受雨。雨水与积尘累积影响现有设施状态的接入参数，具体损坏率待玩法校准。

## 7. 结构事务与存档

沿现有 `View → Command → Foundation System → 规则/Model → 只读投影 → View` 路径。建议结构真值使用单一修订号；楼层边界、导航输入、遮雨覆盖和可见网格都标注来源修订。依赖检查、材料、候选碰撞/导航准备完成后统一提交；异常/取消恢复旧结构与旧导航并返还未消耗预留。不能出现新楼板可见但不可走、已收费但提交失败、旧导航完成后覆盖新布局。

预览只做可解释的便宜规则检查，最终使用候选物理/导航的结果；不每次拖动全车重烘。按受影响楼层/邻接区域失效，先测总耗时再增加更细分块。与当前施工导致居民迁移/临时停车的安全边界接续，拆除会占用中的结构先拒绝。

首次落地结构真值时再升级当前 v9 Schema，不在本次文档阶段加占位字段。需要保存：车架等级/挂点、各层定义、结构实例和宿主连接、门窗逻辑状态/耐久、施工材料与进度、居民层级、攀爬连接 id/两端/量化进度，以及已模拟的积水。支撑区域、导航数据、租约、剖切状态和模型材质从真值重建，不保存第二份派生地板列表。

旧存档迁移创建**旧版矩形尺寸和原点的 0 层**，不能套用新游戏的小甲板挤掉旧设施；通过固定的旧布局映射/快照提供迁移证据，不读取未来会变动的新起步资产作为旧尺寸。先校验结构 id、宿主、层级、孔洞、支撑和预算，再构建物理与导航，最后恢复居民和任务。

攀爬中存档保存确定性动作进度，加载重建有效两端后恢复该连接的独占和脚底位置；若拓扑与存档不一致则明确拒绝加载，保持当前世界，不静默吸附到另一层。取消任务在落脚点结束与全局读档/Context 销毁不同：后者必须终止旧物理执行及其异步回调，然后才让新世界接管。

## 8. 分阶段交付与验证

以下是能力依赖与各阶段验收；排期状态由 Foundation 维护。每阶段都应产出一段可操作体验与对应证据，不按“大量功能完成度”推进。

| 阶段 | 最小实际交付 | 关键证据 / 完成标准 |
|---|---|---|
| S0：美术基准 | 用户选图后，小甲板、三居民、水箱/饮水/厨房/维修设施、一扇分件门窗与局部顶棚样板 | Unity 真实俯瞰/近景与完整旅程画面；设施易认、无耀眼甲板、无材质缺失；顶棚剖切仅验证显示，不声称挡雨已实现 |
| S1：单层局部扩建 | 一次材料投入、外挑小板、梁、有限车架升级和存档恢复 | L/U 形凹口、孔洞、跨板缝、旋转占地、功能净空；拆除依赖/材料守恒；异步提交取消回滚；旧档仍保留旧尺寸 |
| S2：两层与梯子 | 局部上层、合法支撑、一架梯子、可达施工位、切层、跨层任务及攀爬中存档 | 相同 X/Z 不误到岗；高设备/顶梁不穿楼板或侵占净高；两人争梯/暂停/取消/堵出口；携物限制；拆梯冲突；加载无瞬移错层、重复物资或旧执行回写 |
| S3：围护与暴露 | 标准墙段、门洞、窗框玻璃、顶棚，沙尘遮蔽；然后一条雨水/排水后果链 | 门窗逻辑与物理通行一致；开口/缺顶/格栅/雨棚分别验证；切层不改变天气与库存；保存后积水守恒、覆盖变更按时段积分 |
| S4：三四层与体验校准 | 同一套规则提升可建层数和载荷等级，补最必要的运输与拥堵措施 | 三四层重叠拾取、遮挡、楼层导航、上下行队列和存读档；实际目标人口及 GPU/CPU 帧成本、内存、重建耗时；不足则收紧上限 |

S0 期间即可做 S1/S2 的独立灰盒规则 Harness；不把完整多层、天气和围护做完才给用户看到第一版美术。S1/S2 的空间契约稳定后再批量生产墙板/屋顶族，避免按概念图硬做一整辆不可拆的车壳。

### S0 后续的携物通行小实验

先建立独立场景，复用当前工作服 Humanoid、共享动作、同一个可追踪水桶和握点，验证两个平台之间的一段正常尺度楼梯。楼梯提供真实踏面和连续通行输入；角色位置由移动执行拥有，手部 IK 随角色保持桶把手接触，脚部修正只能在声明的踏面范围内寻找接触。首轮重点看上下行、转向平台、桶与膝盖/扶手的净空、半途暂停，以及上下层相同 X/Z 时不会错误判定到岗。

第二步加入与楼梯分开的直梯，验证独占入口/出口、空手攀爬和手提桶拒绝通行；取消在安全落脚点结束，读档恢复确定性连接进度，销毁立即撤销旧执行。最后再接入一块局部楼板及 Renderer 切层，确认隐藏楼板不会停用碰撞、导航或另一层动作。该实验形成接入正式 Foundation 的证据，不在验证前批量迁移全部居民、设施和存档，也不把沿曲线播放人物的演示称为已经完成跨层玩法。

第一步已有[持桶楼梯实机实验](nomad-workshop-stair-traversal-spike.md)：18 级台阶、3.2 m 层高、三维到达判断、同物品暂停/取消/恢复。实机指出必须区分携行导航净空与躯干碰撞半径，并让烘焙跨高和身体跨高一致；这些约束应进入后续连接与居民通行能力配置。正式 S1/S2 结构事务和存档仍按上表推进。

推荐按改动面使用现有 `unity-validation-harness`、`unity-screenshot` 和资产回读流程。新 Harness 优先覆盖过去未经历的失败：孔洞覆盖误判、同平面坐标错层、梯子持有中拆除、候选拓扑异步迟到、切层影响碰撞/天气、旧档被新尺寸裁切。自动几何/身份检查与人工观看分别记录；漂亮截图不替代通路、守恒或性能证据。未出现重复工具摩擦前不新增常驻 AGENTS/Skill 规则；本轮只把设计约束和取证点写入此专题。

## 9. 尚待实机或用户反馈收敛的事项

- 材质明度、设备色组和甲板尺度：用户已认可 J 并要求增加温暖感，当前在独立实机场景校准；不再等待未生成的 K 才开始。
- 标准板尺寸、层高、外挑距离和载荷等级：先用 S0/S1 布局验证，不把生图尺寸当工程规格。
- 三层还是四层为常规上限、梯子是否足够或需要楼梯/吊运：先看 S2 的运输、拥堵和镜头体验。
- 极端结构破坏、车体倾覆、复杂水流和温度/气密模拟：目前没有纳入实现承诺。
