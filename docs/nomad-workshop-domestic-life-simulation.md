# 《游牧工坊》狭小空间生活仿真设计

> 状态：**生活契约与旅途优先范围 v0.5**，更新于 2026-09-05。本文维护生活系统的因果与边界；实施状态和统一开发队列见[Foundation](nomad-workshop-foundation-vertical-slice.md)。下文包含尚未实现的产品方向，不是首版必须一次做完的功能清单。

## 1. 为什么值得做

《游牧工坊》的车辆空间小、居民少，不能靠上百单位和巨型生产链制造规模感。它更适合让少量人、物品和设施持续留下可读后果：一桶水真的被搬到饮水站，一只没吃完的盘子占住台面，沙尘留下污垢，床单偶尔因床上进食而需要拆洗。玩家因此记得“谁在怎样生活”，而不只是看资源数字涨跌。

细节只有满足以下至少一项才进入实现：

- 改变玩家规划或居民决策；
- 产生可见、可追踪且可补救的后果；
- 与已有库存、容器、交互位、任务预留或环境系统复用同一规则；
- 能在调试面板、存档和自动测试中解释与复现。

单纯增加一个数值、动画或点击步骤却没有选择与后果的细节，先留在设计文档中。

## 2. 连续量、有因果随机与短周期人体状态

### 2.1 连续的是物质和状态，不是所有对象

正式模拟优先使用有物理含义的连续量；为了守恒、跨平台复现与稳定存档，底层采用足够细的**定点量化**，而不是让任意 `float` 成为业务真值。例如一升水可以保存为 1,000 mL，玩家看到的是平滑液位，账本仍能精确证明没有凭空增加或丢失。不同领域保留各自量纲，不能再用一个无单位 `int Amount` 同时冒充水、食物和排泄物：

| 状态 | 推荐真值 | 是否连续 |
|---|---|---|
| 水箱、杯子、膀胱液体 | mL | 是，建议 1 mL 量化 |
| 食物与固体排泄物 | g，并按需要另记 kcal / 营养组成 | 是，建议 1 g 量化 |
| 温度、洁净度、健康、疲劳、压力 | 有界标量及明确变化速率 | 是，但语义类型分开 |
| 动作、腐败、维修进度 | 秒或工作量单位 | 是 |
| 杯、盘、零件、居民、床位、交互位 | 稳定实例与个数 | 否，仍是离散对象 |

容量也需要匹配语义：液体容器按体积，货架可同时受体积、质量和离散插槽约束，不能继续用一个“总单位数”解决所有库存。当前 Foundation 已把水、污水和膀胱内容物迁移为整数 mL，并要求每个库存隔间只容纳同一计量维度；食材和餐食暂时仍按件。后续只有在对应玩法真正接入时再增加 g、kcal、Wh、°C 等语义类型，不提前建一套无人消费的单位大全。

### 2.2 随机在事件开始时取样，不在每帧抖动

“几乎所有行为都有差异”是合适方向，但差异必须有来源、可解释、可保存。推荐管线是：

```text
居民基线分布
  → 长期特征 / 健康状态修正均值与离散程度
  → 当前睡眠、疼痛、情绪、饥渴等短期状态修正
  → 工具、设施、天气、车速等情境修正
  → 行动开始时只取样一次目标量 / 输出率 / 事件结果
  → 把已取样结果和随机流序号写入行动检查点
  → 行动过程中按确定速率推进，重大状态改变时才取消或重规划
```

这样同一居民今天可能胃口较小、修理稍慢，但不会每帧忽快忽慢。读档也不会重新掷骰得到另一顿饭。随机流由世界 Seed、居民稳定 id、领域流 id 和事件序号派生；不同居民、不同系统使用独立流，新增一粒尘土的随机数不能改变某人下一顿饭吃多少。开发 Harness 至少显示输入状态、分布参数、Seed / 序号、实际样本和截断原因，并能批量抽样查看分布，而不只显示最终结果。

具体事件采用符合因果的取样方式：

| 事件 | 推荐取样语义 |
|---|---|
| 喝水 | 取样本次目标 mL，再受口渴、胃部余量、杯子和水源库存截断；不是固定喝一整“单位” |
| 吃饭 | 取样目标 g / kcal；饥饿、食物吸引力、恶心、心情和社交情境分别修正均值与波动 |
| 排尿 | 排到“功能性空”基线，排出量由当前膀胱内容决定；流速和动作时长可以有小幅个体波动，不随机留下一个比例 |
| 排便 | 先取样本次绝对目标质量，再以肠道现有内容为上限；不是按库存百分比随机，因此连续多次会逐渐排空 |
| 工作 | 任务拥有固定工作量，取样本次工作阶段的输出率 / 失误事件；不要同时独立随机“效率”和“完成时间”造成双重波动 |
| 污渍 / 故障 | 先判定是否发生，再单独取样严重度；低概率高后果与高概率低后果必须可区分 |

默认不使用简单均匀分布把极端值和中间值设成同样常见。普通个体波动优先三角分布、截断正态或 Beta 一类有中心倾向的有界分布；偏斜的维修时间、疾病恢复等再考虑对数正态。具体分布是数据假设，需要由长跑统计和试玩修正，不把数学名词本身当作真实性。

状态对随机区间的影响也不宜写成“心情差就统一扩大 / 缩小所有范围”。例如低落可能降低平均食欲并让个体波动更大，睡眠不足通常降低注意与工作输出并增加失误，而熟练度可提高均值并减少波动；每种行为显式声明自己读取哪些因果状态。多个结果如果来自同一原因，应共享一段潜在状态，例如本轮疲劳同时影响移动速度和精细工作，而不是分别掷出互相矛盾的随机数。

### 2.3 人体只模拟小时到数日的因果变化

首个周期模型只保留约 24 小时的昼夜节律与睡眠稳态压力：清醒时间让睡眠压力累积，睡眠让它下降；昼夜相位、光照、连续缺觉和个体作息共同影响警觉、注意和体力。这比每天重置一根疲劳条更能生成夜班、补觉和行驶排班选择。参考边界见[睡眠双过程模型回顾](https://pmc.ncbi.nlm.nih.gov/articles/PMC9540767/)与[睡眠剥夺、昼夜节律及表现综述](https://pmc.ncbi.nlm.nih.gov/articles/PMC3963479/)。

不加入月经、固定男性月周期、23 / 28 / 33 天能力曲线或其他长期人体节律。这里的取舍依据是它们对当前核心循环的玩法杠杆不足，而不是试图用游戏规则概括现实中每个人的体验。居民的中短期变化改由能被玩家观察和干预的因果链表达：

- **饥饿与体能分层**：一餐可较快缓解当前饥饿；连续数日摄入不足才逐渐消耗营养 / 体能储备，降低负重、工作输出和恢复速度，重新吃饱后也需要数日恢复；
- **疾病分阶段**：暴露、潜伏、症状和恢复由感染源、休息、营养、治疗与个体易感度推进，不按日历周期自动发作；
- **短期状态**：缺觉、疼痛、晕车、压力、受伤和药物效果在数小时到数日内改变行动收益与风险；
- **缓慢外观变化**：胡须等只作为按生活日推进、可修剪的分级视觉状态，用来表现时间经过和角色生活，不单独制造能力惩罚，也不要求连续毛发模拟。

超过数日的居民状态只有在持续制造新选择时才增加。长时间饥饿留下的体能亏空、严重疾病恢复和伤口愈合属于前因后果的延续，不属于独立的“长周期能力波动”。

### 2.4 存档和调试契约

连续状态保存当前定点量、变化来源和上次推进时刻；随机系统保存每个稳定随机流的序号，以及正在执行行动已经取样出的目标量、输出率和事件结果。读取存档后继续完成原样行动，不重新取样。只有尚未承诺的新决策可以消费下一个随机样本。

正式接线前先保留一个纯 C# 分布 Harness：指定居民快照和 Seed 批量运行至少数千次，检查最小 / 最大 / 均值 / 分位数、守恒、相关性和极端事件频率；再用同一 Seed 复现单次行动。它既服务 AI 自动调试，也防止看似自然的随机参数在长局中产生系统性饥饿或效率崩溃。

## 3. 任务优先级：低优先补货，但不能把所有搬运一概降级

玩家提出的“例行搬运与个人爱好、发呆接近”很适合作为默认节奏：饮水站还有余量时，补满它不是紧急劳动，居民可以先满足爱好或社交。需要保留一个动态升级层，否则所有搬运都低优先会造成明明有水、病人却因没人搬而死亡的荒谬结果。

建议把同一种搬运意图按上下文形成不同候选，而不是给“搬运”职业一个固定权重：

| 情境 | 建议优先级 | 例子 |
|---|---:|---|
| 生存或医疗即将失败 | 极高，可打断低价值活动 | 严重口渴且饮水站为空、急救缺药 |
| 系统即将溢出或造成连锁损害 | 高 | 污水桶将满、腐败食物污染冰箱 |
| 当前需求对应的即时补给 | 中高 | 口渴居民搬一桶水后立刻饮用 |
| 例行补货、清洁与预防维护 | 低到中，并随等待时间缓慢上升 | 饮水站从 1 L 补到 4 L、擦拭轻微污渍 |
| 爱好、社交、发呆 | 与例行补货相近，受性格和压力影响 | 作画、看风景、聊天 |

低优先任务还需要“等待老化（aging）”或最低库存阈值，避免长期被新候选饿死。玩家明确下达的紧急指令、健康危险和容器溢出可临时提高权重，但不应让每次补货都像火警。

当前 Foundation 已先验证其中最窄的一段：居民口渴且站内有水时直接去饮水；站内缺水时，完整候选会估算“取得唯一防漏水罐 → 实际 NavMesh 路程 → 装水 → 交付 → 饮用”，经硬可行性与 Utility 评分后执行；不口渴且站内未满时，同一管线生成低优先级例行补货。没有必要水任务时，原地发呆与随机闲逛以约 2:1 的基础权重进入同一确定性 Softmax，未来爱好会自然分走它们的概率。稳态分布测试使用接近 0 的疲劳 / 压力与最大灰盒闲逛距离；低风险休整显式使用比工作 / 生存决策更宽的相对短名单，防止移动成本先把闲逛裁掉，又不会把同样的放宽错误传播给晕车工作或紧急行为。体内水暂满已改成可恢复背压：等待代谢、排泄压力上升后前往旱厕，并把废物真实转入所属厕所实例桶；停靠清运已接入拆桶、有限接收罐倾倒和回装，见[停靠资源切片](nomad-workshop-stop-resource-ownership.md)。

### 3.1 不做一个无限膨胀的权重公式

复杂性应放进一条可解释的候选管线，而不是散落在居民、厕所、冰箱和车辆脚本中的乘数：

```text
需求 / 工作单生成意图
  → 展开目标、交互位、搬运方式与前置步骤
  → 硬过滤：可达、资源、兼容容器、容量、权限、预留
  → 估算完整计划：取容器 / 洗手 / 行走 / 排队 / 操作 / 收尾
  → 分项计算收益、耗时、体力、风险、个人偏好和环境影响
  → 同意图只保留最佳具体方案
  → 日常 / 紧迫 / 严重 / 危急四级后果仲裁
  → 当前最高可行层内的紧迫度容差 + Top-K / 相对阈值 + 确定性 Softmax 抽样
  → 原子预留并执行；重大变化或承诺期结束后才重评
```

距离不能只读直线米数。候选应使用当前 NavMesh 路径、居民速度、预计排队和全部前置步骤得到“完成要多久”。例如“去餐桌吃”是取餐后走到餐桌再进食，“先洗手再徒手取食”还要加入洗手池、清水和洗手液是否可用。若某一步根本不能完成，候选以稳定原因被硬排除；若只是远、脏、费力或有风险，则保留为软成本，不能混成 `IsAvailable = false`。

各项使用有单位或有明确语义的加减项：舒适、洁净、隐私和社交是收益；行走、排队、操作、体力和预期风险是成本。风险至少拆成“发生概率 × 后果严重度”，居民的风险厌恶再做个人修正。开发轨迹必须能显示每一项，方便判断是设计成立还是参数碰巧凑出结果。

技术形态更接近“Utility AI + 轻量行动配方 / HTN（Hierarchical Task Network，分层任务网络）”，而不是一开始就引入完整 GOAP：饮水、进食、如厕、维修等生活意图的合理步骤大多已知，只需按世界状态展开可选前置与目标。等将来出现大量能任意组合、靠人工配方已经难以覆盖的新工具和替代路径，再用同一前置条件 / 效果数据升级局部规划器；现有 Utility 选择、预留、执行和诊断边界无需推翻。

紧急度会提高延误成本：膀胱压力低时，居民可能多走一段去更干净、更私密的厕所；接近失禁时，较近但一般的厕所更可能胜出。选择行动后保留最短承诺期和切换成本，避免洁净度或距离的微小波动让居民来回改主意。

### 3.2 需求是分开的状态，共用的是压力曲线原语

疲劳、心情、娱乐、社交、姿势不适和膀胱内容物不能压成一根“舒服度”。同一行动可以同时影响多项状态，但每项有独立来源、恢复和后果：

| 状态 | 推荐语义 | 典型行动影响 |
|---|---|---|
| 身体疲劳 / 睡眠压力 | 体力与睡眠需求，不等于心情差 | 睡眠强恢复；站着发呆只小幅缓解；长距离散步可能增加 |
| 健康（正向） | 严重生理失衡、疾病与受伤共同形成的生命结果状态 | 严重缺水连续损害；补水和休息只缓慢恢复；归零即死亡 |
| 心情（正向） | 对当前处境的总体情绪基线 | 安全、舒适、成功、社交可改善；娱乐不足、疼痛、失败和冲突会恶化 |
| 压力（负向） | 生理、环境和执行阻力造成的短期负担 | 发呆 / 闲逛缓慢缓解；缺水、憋尿、阻塞和高疲劳会增加 |
| 娱乐满足（正向） | 是否获得有意义的刺激与兴趣满足 | 爱好强恢复；真正看风景或聊天中等；无内容的发呆和普通闲逛不恢复 |
| 姿势不适 | 久坐、久站或重复姿势造成的局部不适 | 换姿势、走动、伸懒腰恢复；持续同姿势累积 |
| 排泄压力 | 直接由膀胱真实库存 / 容量派生 | 如厕排空；不能由“休息”抽象恢复 |

底层可共用 `NeedPressureCurve` 这类“缺口 → 行动压力”的数学原语，但每项使用自己的开始点、紧急点、形状和重要度。当前膀胱基线在 50% 及以下不单独生成如厕意图，50%–90% 使用端点斜率为零的非线性曲线平滑上升，到 90% 时行动机会达到 100% 并进入紧急候选；它不是在 50% 或 90% 突然跳档。这里的“行动机会”只在一个主要行动完成、失效或低频复评时采样，绝不能每帧掷骰，否则再小的概率也会在几帧内变成必然。

压力曲线只回答需求有多强，不替代完整方案评分。厕所有多远、是否干净、是否有人占用和会不会来不及，仍由候选的路程、排队、卫生、隐私与延误成本表达。达到紧急点后保护“如厕意图”，不强行指定某一座厕所。

当前 Foundation 已实现这次最小拆分：健康、娱乐与心情保存为正向值，疲劳与压力保存为负向负担；低娱乐连续拖累心情并增加压力，高娱乐最多小幅减缓疲劳增长，不能替代睡眠。轻微口渴只驱动饮水，超过严重缺水点后健康损害平滑加速，健康归零进入不可逆死亡阶段。发呆和闲逛连续缓解疲劳 / 压力并略微改善心情，但娱乐仍按时间下降；缺少床椅时还会生成无需路径的坐卧地面兜底，它能有限恢复健康与疲劳，却因舒适不足轻微降低心情。可建造观景画架已经生成首个 `Hobby` 候选，方案包含真实路程、个人作画偏好和三个共享容量的备选停靠位，只有精确到位后的作画阶段才提高娱乐。

工作效率也不再是固定时长：长期基础能力先与健康、疲劳和压力连续合成，可控压力带来短时动员，接近崩溃时增益回落；每段真实工作开始时再从可保存的命名随机流固定采样小幅个人速度差异。健康欠佳和疲劳还会提高费力方案的成本，因此居民更少选择无目的走动或工作、更倾向低体力休息；压力带来的失误与事故风险属于后续独立质量通道，不能用速度增益抵消。

床、椅和医疗尚未接入，后续应提供更高 `RestQuality` 和精确交互位，继续消费同一套身心状态与休息决策。

### 3.3 不是“所有行动随时可打断”，而是所有行动声明中断契约

完全任意的嵌套中断会迅速放大资源、动画、寻路、预留与存档复杂度。首版只保留三层，而且同时最多一个主行动与一个附属活动：

1. **主行动（Primary Action）**：工作、搬运、进食、如厕、睡眠等拥有进度和资源所有权的流程。它声明 `Atomic`、`AtCheckpoint` 或 `Compensatable` 中断政策；默认只在安全检查点自愿暂停。
2. **微活动（Micro Action）**：伸懒腰、调整站姿、从手中杯子喝一口、短暂四顾等几秒且无需导航 / 新硬预留的表现与小结算。兼容时作为主行动上的 Overlay 执行，不销毁主行动，也不重掷主行动已经承诺的随机结果。
3. **绕行子计划（Detour）**：起身去饮水站、去厕所或取得工具等需要导航和设施租约的插入流程。它不是微活动；只能在主行动安全检查点挂起一次，保存续作令牌，并明确哪些材料 / 工位租约保留、释放或返回后重取。

意外、火灾、设施失效等强制中断可以越过自愿规则，但必须按当前检查点执行提交、回滚或补偿，记录结构化原因。首版不做任意深度的行动栈、不允许微活动再触发绕行，也不让 Animator 事件决定资源是否已经结算。这样能表现“工作一段 → 安全放下工具 → 接水 → 回来继续”，同时仍能可靠保存、取消和复现。

## 4. 饮水与水品质

### 4.1 推荐物质链

```text
水源批次 → 车辆水库 / 水箱 → 人工容器或管道 → 饮水站本地库存 → 居民饮用 → 体内水 → 排泄物
```

- 饮水站是有容量的本地缓冲，而不是水库 UI 的远程按钮。
- 站内有水时，居民在饮水站接水并直接饮用，不需要每次先跑去主水库。
- 站内低于目标库存会产生例行补货候选；为空且有人迫切口渴时，同一物质流升级为紧急补水。
- 管道以后可以取代人工搬水的中间步骤，但不能让来源、流量、品质和断供原因消失。
- 水不能进入普通随身库存后凭空搬运。人工搬运至少需要 `LiquidTight` 的桶、壶或罐，并受其容量、洁净度和取得路径影响；管道是另一种搬运能力，不是无限容器。

### 4.2 水不腐败，但有品质

水量与水品质应分开。首个品质模型可以只保留一个量化指标和少量污染标签：水源初始品质、过滤器效率、储存容器洁净度和污染事件共同决定饮用风险。水不会像食物一样仅因时间自然过期，但脏容器、管道倒灌、毒尘或未经处理的水源可以降低品质。

不建议首版同时模拟矿物质、酸碱度、细菌、盐度和温度。只有当某项能影响过滤方案、健康后果或区域选择时再加入。

## 5. 进食地点是一组可组合的情境规则

居民携带一份装盘食物后，可以从可达、未占用的进食情境中选择。地点不应由一串针对具体 Prefab 的 `if` 决定，而是提供能力标签和参数，例如 `CanEatHere`、舒适度、社交机会、占用时长、弄脏概率与污染严重度分布。

| 地点 | 主要收益 | 代价与风险 |
|---|---|---|
| 餐桌 | 最佳心情恢复、较好的社交机会、容易清洁 | 需要空座位和空台面 |
| 研究台 / 工作桌 | 就近、节省行走 | 妨碍研究或工作，可能污染食物或精密设备 |
| 床 | 私密且疲惫时方便 | 弄脏概率可较低，但一旦发生往往严重，可能要拆洗床单 |
| 地面坐食 | 随处可用 | 舒适与卫生较差，恢复值较低 |
| 站立进食 | 最快、几乎无需设施 | 心情恢复最低，疲劳时吸引力更低 |

“发生概率”与“发生后的严重度”必须是两个变量。床上吃饭可以因居民小心而不常弄脏，但命中后更容易形成大面积织物污渍；餐桌更常出现少量碎屑，却容易擦净。性格、疲劳、动作熟练度、食物类型、载具颠簸和天气可在以后修正这两个分布。

徒手拿一小份食物可以作为没有盘子时的退路，但运量应由食物定义的 `BareHandsMaxAmount` 限制。手部污染会增加食物污染暴露，再由食物状态、免疫 / 健康和后果严重度形成食物中毒风险；这使“先洗手”“拿干净盘子”“冒险就地吃”成为真实方案，而不是一个固定卫生扣分。货物还可声明是否允许容器：大件或姿态敏感物品可以要求双手直接抬运，不能因为某只箱子容量数字足够就塞进去。

这类细节应先以少数离散结果验证是否好玩，不立即上连续流体污渍或布料物理。

## 6. 餐具、剩余食物与台面空间

### 6.1 明确物品，不做抽象“整理货物”

- 杯子、盘子、食物份和清洁工具拥有稳定实例 id；需要搬运时，物品真的从一个容器或表面转移到居民携带位，再转移到目标。
- 盘子记录内容物、剩余量、温度、制作时间与污染状态。进食结束不保证清空。
- 剩余食物可以连盘放回冰箱；冰箱减慢新鲜度衰减而不是把保质期重置。
- 饮水剩余可以留在杯中。纯水本身不过期，但杯子洁净度和外来污染仍有后果。

### 6.2 放置区域与精确插槽

桌面、研究台、床头、柜台和玩家指定的地面堆料区默认暴露可计算的 `PlacementRegion`，而不是把所有表面都切成少量固定点。区域在支撑对象局部平面中记录稳定 id、边界、高度、用途标签、质量/高度/类别约束和已放置物品的局部姿态；物品用自己的二维 footprint、边距和允许方向判定是否能放下。

杯架、插头、武器挂点和机器内部料仓等需要精确对齐的位置仍使用容量一的 `PlacementSlot`。居民站在哪里、面向哪里则继续由 `InteractionGroup / Slot` 负责，不与物品放置容量混成一个概念。

当表面没有合法姿态时，居民不能把杯盘“塞进空气里”：他需要继续携带、寻找其他允许表面、生成真实整理任务，或把剩余食物送回冰箱。无居民动作的自动“挤一挤”不作为默认副作用，避免物品瞬移、预留失效和存档抖动。完整几何、地面 Zone、IK、蓝图到料和施工规则见[世界物品放置与蓝图施工设计](nomad-workshop-world-placement-and-construction.md)。

## 7. 污染、清洁与耐久使用相似的时间变化骨架，但不共享一个万能数值

食物腐败、设施老化、居民疲劳和表面变脏都具有“随时间变化、被环境修正、经行动恢复”的共同形状，可以复用：

- 稳定对象身份与状态版本；
- 基础变化速率 + 环境修正项；
- 阈值事件与可解释来源；
- 行动结算、取消和存档恢复规则。

但它们的单位、边界和后果不同，不宜塞进一个名为 `Durability` 的万能组件。更合适的是共享时间推进 / Modifier / 阈值机制，由 `Freshness`、`Condition`、`Fatigue`、`Contamination` 等领域状态各自定义语义。

这类连续状态不需要每帧遍历全部对象。对象保存当前量、上次结算时刻和仍然有效的速率来源；被观察、使用、保存或跨过计划阈值时再按统一模拟时钟积分。只有正在发生泄漏、燃烧等需要连续交互的少数事件进入活跃更新集合。

### 7.1 脏污缓慢积累，但来源和清洁办法必须具体

卫生也不能只有一个万能条：

- **手部污染**直接影响徒手接触食物、伤口和洁净物品，洗手是短动作；
- **身体卫生缺口**影响舒适、社交和长期健康，洗澡是消耗更多水、时间和隐私设施的行动；
- **设施 / 表面污染**属于具体世界对象，决定使用风险和清洁任务；
- **水与食物污染**跟随批次和容器流转，不能因居民洗澡而自动清零。

洗手效果以后由水品质、用量、洗手液和设施能力共同决定。没有清水或洗手池不代表禁止进食，而是让安全方案不可用，并留下更快但风险更高的替代方案。

污染至少区分“位置、类型、强度 / 质量、清洁难度”。某一对象的积累速率来自明确来源：环境暴露、具体使用行为和已有污染扩散，减去密封、防护及清洁效果。例如沙尘天气提高外露表面和进气设施的积尘速度，做饭给附近表面留下油污与碎屑，厕所事故产生生物污染；不能用一个全局系数让所有对象等速变脏。

连续强度只在少数可读阈值改变表现和任务：薄尘先改变材质与检查说明，中度积尘降低散热或卫生，厚尘才生成较高优先级清扫。轻微桌面碎屑可擦拭；严重床单污渍可能把床单变为一个待拆卸、搬运、清洗和晾干的物品。清洁任务同样遵守真实工具、清洁介质、污物去向和容量约束，不要求为每粒尘土创建世界对象。

### 7.2 老化、维护欠账和实际损坏分层

设施不使用一根“耐久条”同时代表年龄、脏污和是否可用。建议至少分三层：

1. **老化 / 等效磨损（Wear）**：由运行时长、负载、振动、冷热循环和恶劣环境缓慢累加。它通常不能靠一次普通修理清零，只有大修或更换关键部件才明显恢复；
2. **维护欠账（Maintenance Debt）**：润滑、紧固、清洁滤网等可逆保养需求。及时保养会降低当前故障风险和后续磨损速度，但不能把旧设备变成新设备；
3. **损伤与故障（Damage / Fault）**：已经发生的漏水、卡死、短路、性能下降等具体状态。修理消耗对应零件和工时恢复功能，若底层老化未处理，同一设备以后仍更容易再次故障。

这三层会形成“继续冒险运行、停车保养、携带备件、彻底大修或替换”的选择。积尘、超载、沙尘暴、快速越野造成的振动等都通过命名修正项进入磨损或故障风险；不同设施只读取与自己有关的来源。

#### 当前 Foundation 的已实现语义

现阶段只有主车辆水箱拥有非零暴露参数，数值是为快速观察的 Harness 节奏，尚未平衡。默认每个十分钟生活日约增加 `10.2‰` 等效磨损、`150‰` 维护欠账和 `100.2‰` 积灰。当前故障风险率为：

```text
50 基础微风险/秒
+ 1 × 等效磨损‰
+ 2 × 维护欠账‰
+ 1 × 积灰‰
```

因此等效磨损表示“这台设备的底子已经多旧”，普通保养不降低它；维护欠账表示“有多少该润滑、紧固、清洁却还没做的可逆工作”，本轮清洁保养会最多降低 `550‰` 欠账和 `500‰` 积灰。保养会立即降低以后的风险率，但不倒扣已经累积的历史风险；修理出水阀会开始新的预取样故障周期，也不会顺带清零磨损、欠保养或积灰。

它们目前已经改变故障风险和警告等级，具体“出水阀卡滞”会阻止新的取水方案。“维护欠账加快未来磨损、磨损降低容量/效率、不同部件有不同故障谱”仍是后续设计，不应把文档目标误说成当前已实现。

### 7.3 故障是随风险积累触发的离散事件

“越老越容易突然坏”不应实现为每帧掷一次固定百分比。设施先根据老化、维护欠账、污染、负载和环境得到瞬时风险率 `lambda(t)`，再累积风险积分：

```text
累计风险 H += lambda(t) * deltaTime
当 H >= 预先取样并保存的故障阈值 H* 时触发故障
```

`H*` 由设施自己的确定性随机流在新部件启用或上次故障结算后只取样一次；标准实现可由均匀样本 `u` 得到 `H* = -ln(1-u)`。这样暂停、加速、不同帧率和不同结算步长不会改变同一存档的故障时刻。触发时再一次性取样故障模式和严重度；候选由设施部件、当前负载、环境和磨损共同决定，例如水路更可能泄漏，传动机构更可能卡死，电气过载更可能短路，而不是统一变成 `Broken = true`。

随机故障必须提前给玩家可行动的信息：噪声、渗漏、温升、效率下降、检查结果或风险分档至少暴露一部分；保养能改变风险，关键系统允许准备备件或冗余。未知小故障可以制造故事，完全不可预防的致命故障只会制造惩罚。开发 Harness 应能显示当前风险来源、累计风险、阈值、预计风险区间和已取样结果，但普通玩家界面只显示可理解的健康与预警。

## 8. 温度、电力与管道的接入顺序

这些系统都值得保留，但不与第一份餐食同时铺开：

1. **电力**：先验证一个生产者、一个储能、饮水过滤 / 冰箱两个消费者和断电后果；
2. **温度**：先做舱室或区域级温度，而不是每个体素；影响居民舒适、食物腐败和设备效率；
3. **管道**：先做水库—过滤—饮水站 / 排污箱的端点与连通图；无管道时保留人工搬运替代路径；
4. **更细环境**：只有热区、风沙、冻结和污染已经产生可读选择后，才增加局部传导、压力或复杂流量。

### 8.1 生活时钟与压缩气候年

居民生活和气候季节使用同一个可暂停、可加速的模拟时钟，但读取不同的相位尺度：

- **生活日**保留 24 小时语义，驱动饮食、排泄、睡眠、工作、疾病恢复和胡须等数日变化；
- **气候相位**约快七倍：每经过一个完整昼夜，季节日历前进一“气候周”；暂定每季 12 个生活日、完整气候年 48 个生活日；
- UI 优先显示“第几循环年 / 季节 / 本季第几周”，不伪装成与现实公历逐日对应的 365 天。

这保留了“一次昼夜能感到季节在前进”的压缩感，又不必宣称居民一天只吃了相当于一周的食物、一次睡眠跨过七天。初始节奏假设为 `1x` 下一个生活日约 10–12 分钟：20–30 分钟的路程约跨 2–3 个昼夜，一季约 2–2.4 小时，完整气候年约 8–9.6 小时；加速、暂停和玩家实际节奏会改变墙钟时间。这些都是原型参数，必须用长跑和试玩检查旅途、夜晚、作物、疾病与季节压力是否相互抢节奏。

季节变化连续插值，不在某天零点瞬间换皮。温度基线、降雨 / 风沙倾向、日照长度和区域资源逐步变化；天气仍由区域与天气系统产生，不是“冬天每天必下雪”。首版只需要统一时钟、昼夜和一种沙尘压力，四季内容等核心旅途成立后再接入。

### 8.2 车辆运动与晕车

车辆速度不是直接写进所有行动权重的全局乘数。运行时先由车速、加速度变化、路面颠簸和持续时间形成运动暴露，再按居民易感度累积晕车；低速、停车、躺卧和合适药物让它恢复。行动方案只读取当前晕车状态及自身的工作强度 / 休息质量：高强度维修成本上升，躺卧休息收益上升，严重时才生成呕吐或无法工作的紧急候选。

这样以后调整“快速行驶是否值得”时，可以同时看到路程时间、燃料、居民晕车和工作效率，而不是用一个不透明的 `workWeight *= 0.5`。晕车是需要保存的居民状态；逐帧加速度缓存和表现摇晃可以重算，不进入存档。

这些网络都应能解释“为什么停止工作”，并让玩家在建造预览时看到端口和连接，而不是建成后才从日志猜问题。

## 9. 建造时实时显示交互位与可达性

正式 Foundation 的设施占用和导航是连续平面规则；可视网格只是可关闭、可调步长的玩家辅助。位置档位为自由、0.2 / 0.3 / 0.4 / 0.6 m：自由模式不吸附也不显示网格，其他档位以甲板原点为共同原点，并都是内部 0.1 m 基础格的整数倍。基础格只保证档位间没有原点或浮点漂移，不意味着 0.3 m 上的每个旧设施也必然落在 0.4 m 网格线上；切换档位不会移动已建成设施。当前实现采用两级验证：

1. 指针位置或旋转改变时，先做精确有向矩形的越界 / 重叠检查；
2. 几何通过后，用 0.1 米采样、75 mm Slot 映射半径和复用 NavMesh Agent 净空的八方向 Flood Fill 做保守实时预检，并逐个标记候选交互位；
3. 玩家确认后，仍以异步 Unity NavMesh 重建和精确路径采样作为最终事务裁决；失败完整回滚。

按当前 0.2 m Agent 半径、0.09 m Voxel 和甲板尺寸共有 8,320 个预检采样格；缓冲数组复用，不在每格生成对象，也不会拖动一帧就重建一次 NavMesh。开发面板显示本次耗时、访问格数和可达交互位数，以真实数据决定以后是否需要分帧、脏区更新或降低采样精度。最多 64 个候选交互位属于当前预览状态的明确上限，不是未来正式设施容量目标。

实时预检刻意偏保守：它适合提前阻止明显堵路，不替代 NavMesh 的最终答案。若灰盒试玩出现大量“预览红但实际可走”的误判，应优先调整净空、端点采样和采样分辨率，而不是悄悄允许玩家无视提示。

## 10. 存档真值

生活细节需要随时保存，但不保存 Unity 组件的瞬态内部状态。未来运行存档至少需要覆盖：

- 设施、容器、放置区域/精确插槽与物品的稳定 id、所有权关系、局部放置姿态及容器污染；
- 杯盘内容、剩余量、新鲜度、水品质、分类污染和设施状况；
- 居民需求、当前位置、当前意图、任务租约与是否已经提交结算；
- 居民手部污染、身体卫生缺口和晕车等会跨行动持续的状态；排泄压力若能由膀胱真实库存与代谢进度重建则不重复保存；
- 各领域确定性随机流的序号，以及当前行动已经取样出的目标量、输出率和事件结果；读档不得重新掷骰；
- 统一模拟时刻、生活日相位和气候年相位；季节表现可重算，已经影响资源或事件的结算不能重掷；
- 设施的等效磨损、维护欠账、具体故障、累计风险与已取样故障阈值；读取后继续同一条风险轨迹；
- 清洁 / 制作 / 搬运动作的可恢复检查点；
- 温度、电力和管网的确定性输入；可重算的缓存与 NavMesh 路径不写入存档。

加载后先校验引用和容量，再按稳定 id 重建预留，最后重新寻路。任何物品都不能因为取消、保存或加载同时出现在居民手中和容器里。

## 11. 推荐实现节奏

### 已进入当前 Foundation

- 饮水站本地库存、迫切饮水与低优先例行补货分流；
- 连续建造实时通路预检、候选交互位标记、确认后的可回滚 NavMesh 事务；
- 唯一防漏水罐的设施旁 / 居民手中位置、独立内容库存、全周期预留，以及水罐 → 饮水站 → 身体的守恒证据；
- 水、污水与当前尿液以 1 mL 定点量进入同一资源账本；车辆水箱、水罐、饮水站、体内、膀胱与厕所分别有真实容量，界面按数值自动显示 mL 或 L；食物件数不能再误存入液体容量；
- 纯 C# 完整行动估算器：步骤时长、距离、舒适 / 洁净 / 隐私 / 社交收益、体力、风险、紧急延误和晕车修正均保留命名分项；结果再接入既有 Utility AI。
- 纯 C# 风险仲裁器：硬可行性先于风险，风险层先于同层紧迫度，容差内再比较完整 Utility；危急层默认确定性，负效用但可执行的应急方案仍作为最小伤害选项。正式 Foundation 已把如厕、直接饮水、搬水补货、散步、发呆和观景作画接到同一入口；火灾、疾病与多人事件分配仍只有纯规则边界，尚未成为运行时玩法。
- 货物—容器能力匹配：水要求防漏容器，已经由正式 Foundation 正向执行并用“非防漏水罐”反向阻塞；食物可允许少量徒手搬运并把手部洁净度折算为污染暴露，目前仍只锁定纯规则，不代表场景内已有餐具和洗手动画。
- 统一模拟 Tick、生活日 / 气候相位与领域隔离的随机游标已进入运行检查点；确定性沙尘已驱动场景表现与水箱积尘、欠保养、磨损和风险积分；出水阀卡滞会阻止取水，居民能取得实体维修包并在服务阀完成原子消耗。有限驿站备件已接入；完整昼夜光照、季节与其他设施故障仍未接入。

### 下一条最小生活链

近期生活开发服务于一次完整旅程：厕所实例库存、有限停靠水源、污物接收罐与实体备件已接线。离开、重返和读取存档均不得刷新已耗尽的地点资源；取货、交付与消耗继续使用真实账本。清运搬走厕所原桶，到达接收口才倾倒，回装前所属厕所停用；满膀胱与满桶同时发生时，清运仍须作为恢复如厕的前置工作。当前只有三份有限维修包和单居民，仍有原型限制，不能凭短时长跑通过就认定能持续生存。全项目顺序只在 Foundation §9 维护。

当前固定 300 mL 饮水、8 秒灰盒代谢与 1:1 尿液输出是可替换玩法参数。真实单位保留，未来汗液 / 呼吸等损失需有显式去向。行动随机、检查点和水箱状况 Harness 已存在，应扩展同一证据链，不重新建一套状态。餐食、洗手、餐具和冰箱的组合方案保留为旅途试玩后的内容候选；完整餐饮链不阻塞首段旅程。

### 随后验证

- 桌面轻微污渍与一次擦拭；
- 已有沙尘 / 设施风险联动在旅途中的预警、频率和维修负担；
- 床上进食的低概率高严重度污渍，以及床单拆洗是否值得保留；
- 餐具清洗与污水去向；
- 已有爱好 / 发呆 / 补货与驾驶、召回的 Utility AI 竞争和安全中断；
- 一个区域温度、最小电网和最小水管网；
- 统一时钟上的昼夜表现；四季只在一条旅途与天气循环已经好玩后接入。

每一阶段都要求 Model / System / View 分离、Inspector 可观察、稳定存档字段、取消安全、自动测试和一次实际视觉检查。真实试玩若证明某个细节只增加等待和微操，就应合并、自动化或删除；生活感是目标，繁琐不是目标。
