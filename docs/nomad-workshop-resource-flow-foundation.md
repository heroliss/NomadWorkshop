> 状态：**同量纲库存 + mL 水循环 + 世界物品 Use Lease + 实体物流接线已验证 v0.5**，更新于 2026-09-05。它证明真实库存、任务预留、实体容器、设施加工、连续需求、按毫升代谢、容量背压，以及一个落地物品从精确来源被拿起并原子消耗可以形成可观察闭环；尚未证明三名居民调度、完整供应链、长期平衡或这条链已经好玩。

## 1. 这一轮回答的问题

这一步没有继续增加一种抽象的“整理货物”数值，而是回答七个更基础的问题：

1. 一份资源从哪里来、正被谁持有、最终去哪里，能否在任意时刻说清楚；
2. 两名居民竞争同一份资源、同一格目的容量或同一交互位时，能否在任务开始前全有或全无地预留；
3. 任务中断时，已经拿在手里的货物是否仍然存在；
4. 设施加工能否同时验证全部输入与输出容量，再在一个提交点结算，而不是先吃掉材料后才发现污水无处可放。
5. 饮水能否同时影响连续口渴与真实水库存，而且行动取消时两者都不改变；
6. 喝下的水能否先留在体内、延迟成为排泄物，再经膀胱、厕所暂存桶和人工清运进入车辆废物罐。
7. 一个有体积和精确支撑位置的消耗品，能否在使用期间保留来源所有权、拿起后从世界消失、成功时才消费，并在取消或中途检查点时准确恢复。

当前可见流程是：

```text
食材储柜 ─┐
           ├─ Ada 随身库存 ─→ 厨房输入口
净水箱 ───┘

厨房输入口：食材 × 1 + 清水 500 mL
       └─ 原子加工 ─→ 厨房餐食口 × 1 + 厨房污水口 500 mL

厨房餐食口 ─→ Ada 随身库存 ─→ 成品餐架
厨房污水口 ─→ Ada 随身库存 ─→ 车辆废物罐

净水箱 ─→ Ada 随身库存 ─→ 饮水台 ─→ Ada 体内待代谢水
                                      └─ 延迟代谢 ─→ 膀胱排泄物
膀胱排泄物 ─→ 厕所暂存桶 ─→ Ada 随身库存 ─→ 车辆废物罐
```

厨房只把产物放到自身的本地输出口。餐架和车辆废物罐即使在同一辆车上，也不能被加工结算跨空间写入；后两段仍然是真实搬运。厨房污水与当前尿液共用容量为 1 L 的液体废物罐，但保留各自资源身份；剩余容量不足以容纳下一批时，清运任务会保留原容器里的物质并报告目的容量不足。

## 2. 模拟层契约

### `ResourceInventory`

- 每个库存有稳定 `Id`、计量维度、以该维度基础单位表示的总容量，以及按 `ResourceId` 记录的整数数量；
- 构造时可以给出初始内容，运行期只有资源流账本可以改写；
- 读取接口提供当前数量、总量、剩余容量和排序后的内容快照；
- `ResourceMeasure.Item` 表示件，`ResourceMeasure.Milliliter` 表示 mL；资源、来源、携带容器和目的库存量纲不一致时立即拒绝，不让“1 件食物 + 300 mL 水”形成无意义总容量；
- 一个库存隔间只容纳一种计量维度。厨房、居民或车辆这类复合所有者通过多个库存表达物品格与液体容器，而不是退回万能 `Amount`。

### `ResourceFlowLedger`

`TryReserveHaul` 在一次单线程模拟操作中共同验证并预留：

- 来源的指定资源数量；
- 居民随身库存的容量；
- 最终目的库存的容量；
- 任务需要的来源与目的交互位。

资源流还会自动把稳定任务 id 纳入同一批预留；即使两个候选碰巧使用不同物品和交互位，同一个任务也不能被两名居民重复领取。

任一条件失败都返回结构化 `ResourceFlowBlocker`，而且不会留下部分预留。预留本身不移动资源；`PickUp()` 才把资源从来源结算到居民随身库存，`Deliver()` 再从随身库存结算到目的地。

若在拾取前取消，所有预留释放且库存不变。若在拾取后取消，资源仍留在居民随身库存，句柄用 `CargoRequiresRecovery` 明确要求重新派送或落地，不能静默删除。

`TryReserveProcess` 同样先锁定全部输入、输出所需净容量和工作位。`Commit()` 同时扣除输入并写入输出；取消则不发生任何经济结算。同一库存内加工时，本次输入释放的容量可以被本次输出复用，但不能预支其他尚未完成任务未来可能释放的空间。

### `PlacementRegionLedger` 的 Use Lease

库存账本适合“多少件 / 多少毫升在容器之间移动”，但维修包、杯具和水罐还需要回答“具体哪一个物体占据哪个支撑区域”。`PlacementRegionLedger` 因而独立维护世界物品 footprint、稳定候选姿态和事务所有权：

- `TryReserveUse` 先锁定一个已落地物品，但不立即删除它，其他任务仍能看见它存在却不能重复领取；
- `PickUp` 后物品暂时离开世界落位，Use Lease 继续持有精确来源区域与局部姿态；
- `Consume` 只在业务结果提交时让物品永久消失；
- 未提交的 Lease 在取消、重规划或检查点捕获时恢复到原始来源，不随机寻找一个“差不多”的空位；
- 区域删除、占用查询、冲突检测与快照都认识正在使用的物品，避免半行动状态绕过容量或复制实体。

首个正式消费者是车辆水箱维修包：居民从 `maintenance-tray` 的 `maintenance-supply` 功能组取件，携带到 `service-valve`，只有维修完成才原子消费。该原语刻意不包办堆叠数量、腐败、耐久或配方，它只解决落地实体在使用事务中的守恒。

### `ResidentWaterCycle`

- `Thirst` 是 0 到 1 的连续需求；喝水任务只有在提交时才同时转移水并缓解口渴，预留后取消不会扣水或改需求；
- 喝下的水先进入居民私有的 `BodyWater` 库存；玩法速率可产生不足 1 mL 的累计余量，账本只在满 1 mL 后原子转移，因此不同帧步长不会丢量；
- 当前一份饮水是 300 mL，体内待代谢容量 900 mL，膀胱容量 500 mL；`ExcretionPressure` 直接读取膀胱实际 mL / 容量，排尿提交当前膀胱全部内容而不是随机留下一个比例；
- 膀胱满时，待代谢水与累计进度原地保留；厕所桶满时，如厕行动不提交。两种情况都返回结构化容量阻塞；
- 如厕只把排泄物转入厕所暂存桶，之后仍需普通搬运任务完成“厕所 → 随身库存 → 车辆废物罐”。

当前 1 mL 饮水最终对应 1 mL 膀胱内容物，是为了验证守恒、延迟与容量背压，不是现实生理比例。以后可增加汗液、呼吸散失等显式去向并重新平衡速率，但不能只乘一个系数让物质无记录消失；固体排泄物未来应使用 g 与独立资源，不塞进当前 mL 液体链。

### 为什么没有做万能物品组件

资源 id 可由内容继续扩展，但当前账本只解决“整数定点量在同量纲库存间如何安全流动”。食物腐败、温度、设施磨损、居民疲劳和地面污渍仍保留各自语义；只有真实需求证明它们共享相同生命周期与查询方式后，才提炼更小的数学原语，不先创建一个包办所有状态的 `DurabilityComponent`。

## 3. Unity 表现 Harness

场景 [`FoundationResourceFlowSpike.unity`](../Assets/Game/NomadWorkshop/Scenes/FoundationResourceFlowSpike.unity) 由菜单 `Assets/SSFramework/游牧工坊/Foundation/创建或打开实体物流灰盒` 创建或更新。它接入：

- 参数化野战厨房 Prefab；
- 已验证的 Humanoid、共享 Animator Controller 和程序假人回退；
- 食材储柜、净水箱、厨房本地输入 / 输出、餐架与车辆废物罐；
- 饮水台、干式厕所、厕所暂存桶，以及体内水 / 膀胱内容物的诊断状态；
- 居民手上的食材箱、水罐、餐盘、污水桶和排泄物暂存罐表现；
- 由任务阶段直接驱动的厨房门 Pivot；
- 左侧开发面板中的当前任务契约、阶段、全部库存和结构化阻塞原因。

动画、门和手持物只呈现资源流结果。没有用动画事件扣库存，也没有因为画面已到达目标就绕过 `PickUp()` / `Deliver()` / `Commit()`。

这一场景是 Desktop Foundation Harness，不是正式 UI 或最终关卡：镜头使用固定正交斜俯视，左侧保留独立诊断区域；移动仍是甲板上的直线插值，尚未接入可通行网格、路径拥堵或 Animation Rigging。

## 5. 有意保留的边界

- 旧单体 Harness 仍只有 Ada 和一条固定任务链；正式 Foundation 已将如厕、直接饮水、搬水补货、散步和发呆的完整方案放入同一次 Utility 决策，并能在高风险候选不可行时保留诊断、继续执行可行备选；尚未证明多居民竞标、长期平衡或真实灾害任务。
- 库存已经区分“件”和“mL”，但同一隔间目前仍只有一种总容量；尚不处理物品形状、堆叠、重量、液体质量或居民负重速度；
- 搬运任务在领取时同时占用来源和目的交互位，简单可靠但可能过度保守；多人实测若出现无意义等待，再拆成任务预留与近场交互预留两个阶段；
- 正式 Foundation 已有水罐、搪瓷杯和维修包三种落地世界物品：杯具验证区域间原子移动，维修包验证通用 Use Lease；但还没有可堆叠数量、重量 / 负重、自动整理、通用库存—落地转换或备件补货制造；
- 口渴增长、每份 300 mL 的缓解、8 秒灰盒代谢和各容器容量都是可观察性 / 玩法参数，尚未经过长局平衡；真实单位不表示当前速率就是医学模型。正式 Foundation 已接入健康、疲劳、心情和娱乐的首版联动，但营养、卫生、水质、疾病和热量仍未进入这条资源链；
- 旧 Harness 只允许主动运行一次水循环；正式 Foundation 已能自主执行饮水 / 补水 / 如厕，并接入有限驿站取水、整桶污物清运、途中召回和安全检查点。多人租约让渡仍待验证。正式清运搬动厕所原桶，到驿站才倾倒内容，具体所有权见[停靠资源切片](nomad-workshop-stop-resource-ownership.md)。
- 没有管道。未来管道必须消费和写入同一库存接口，只替代运输劳动，不能另建一套会生成或吞掉资源的快捷数值。

## 6. 服务于首段旅途的物流验证

统一开发顺序见 [Foundation §9](nomad-workshop-foundation-vertical-slice.md#9-下一步形成一次完整旅程)。以下是物流专题的验收维度，不是一条独立于旅途的实施队列。

1. 一次性维修包耗尽已有可解释诊断；首个有限停靠点接入水和备件来源。库存、落地物、搬运与使用继续复用现有账本，重返或读档不重新生成已取走物资。
2. 厕所实例库存、有限清运与备件来源已接线，继续验证多人竞争。`UtilityDecisionEngine` 只选意图，行动执行器独立持有资源流句柄、Placement Lease 和中断原因；资源已提交不代表容器和居民已完成归车。
3. 增加第二名居民，专门验证两人竞争水、维修包、厕所、废物罐容量与中断恢复，而不是立刻扩到三名完整角色和几十种任务。
4. 记录多 Seed / 多生活日中的等待、步行、故障、备件消耗、口渴和厕所背压，判断生活链是否形成空间与劳动取舍；参数不成立时先改粒度，不叠加新需求。
5. 当任务契约稳定后，再建立人和 AI 共用的薄 Editor 观察工具；当前 OnGUI 面板足以诊断，不提前维护第二套编辑业务逻辑。

如果水 / 排泄链只制造机械跑腿而没有形成容量、布局、优先级和照料感，应先修改任务粒度或设施规则，而不是继续叠加洗澡、垃圾、管道和清洁系统。
